# Handoff

세션 **중간 이탈의 오케스트레이터**. `/work`가 "lifecycle 완주"라면, Handoff는 "미완료 상태에서 바톤 터치".

## 사용법

```
/handoff                     # 현재 세션 정리 + 핸드오프 문서 생성
/handoff <메모>               # 추가 메모와 함께 핸드오프
```

## Step 0: 미소비 핸드오프 탐지

`docs/handoff/handoff-*.md`를 확인한다. 존재하면 사용자에게 먼저 보고:

> "미소비 handoff N건: [목록]. 이어서 처리할까요, 새 handoff 생성할까요?"

- 이어서 처리 → 해당 파일을 읽고 컨텍스트 복원
- 새 handoff 생성 → Step 1로 진행

없으면 바로 Step 1.

## Step 1: 커밋

uncommitted 변경이 있으면 커밋한다.

```bash
git status
```

- 변경 있으면 → `/commit` 스킬의 프로세스로 커밋
- 변경 없으면 → 건너뛴다

⚠️ 커밋 훅([`secret-scan.sh`](../../scripts/secret-scan.sh) · [`safety-boundary-check.sh`](../../scripts/safety-boundary-check.sh) · [`pre-commit-check.sh`](../../scripts/pre-commit-check.sh))이 막으면
**`--no-verify`로 우회하지 않는다.** 훅이 막은 사실 자체가 다음 세션이 알아야 할 정보다 — 핸드오프 문서의 「주의」에 적는다.

## Step 2: 세션 요약 생성

이 세션에서 한 일을 구조화한다.

1. **세션 커밋 추출** — 세션 시작 시점의 HEAD부터 현재 HEAD까지 `git log --oneline` 추출
2. **변경 요약** — 각 커밋의 핵심을 한 줄로
3. **관련 문서** — 이 세션에서 참조/생성한 PRD, Plan 파일 경로

## Step 3: 남은 것 식별

미완료 작업을 구조화한다.

1. **대화에서 추출** — "남은 것", "다음에", "TODO", "아직" 등 미완료 시그널
2. **활성 Plan** — `docs/plans/PLAN-*.md`에서 미구현 단계
3. **사용자의 명시적 언급** — 직접 지시한 남은 작업
4. **미결 의존** — 이 작업이 [`open-questions.md`](../../rules/context/open-questions.md)의 어느 항목에 걸려 멈췄는가
5. 각 항목에 **우선순위/순서 힌트** 부여

## Step 4: 핸드오프 문서 생성

`docs/handoff/handoff-{YYYY-MM-DD}-{slug}.md` 파일을 생성한다.

### 템플릿

```markdown
# Handoff: {제목}

> {날짜} 세션에서 {한 줄 요약}

## 완료

| 커밋 | 내용 |
|------|------|
| `abc1234` | 설명 |

## 남은 것

### 즉시 (다음 세션 첫 작업)
1. [구체적 작업] — [관련 파일/문서]

### 이후
- [항목] — [맥락]

### 미결에 막힌 것
- [항목] — `open-questions.md` Q-{번호}. {확인해야 할 대상}

## 컨텍스트

- **브랜치**: `{현재 브랜치명}`
- **빌드 상태**: `./gradlew build` {통과 / 실패 — 사유}
- **PRD**: `docs/prd/PRD-{issue}.md` (있으면)
- **Plan**: `docs/plans/PLAN-{issue}.md` (있으면)
- **PR**: {URL} (있으면)
- **주의**: [다음 세션이 알아야 할 것 — 훅이 막은 사항, 임시 우회, 검증 안 된 가정]

## 안전 경계 상태 (해당 시)

작업이 S-1~S-6에 닿았다면 어디까지 확인됐는지 남긴다.

| 조항 | 상태 |
|------|------|
| S-? | {방어 구현됨 / 미확인 / 리뷰 필요} |

## 다음 행동 제안

`/work {issue}`로 시작하면 재진입 감지가 이 브랜치와 커밋을 인식해 이어간다.
구체적으로: [첫 번째로 해야 할 일]
```

## Step 5: Memory 저장

핸드오프 문서의 핵심을 memory에도 저장한다 (project 타입). 다음 세션의 memory 로드 시 핸드오프 존재를 인지할 수 있도록.

```markdown
---
name: handoff_{date}_{slug}
description: {날짜} 세션 핸드오프 — {한 줄 요약}
type: project
---

핸드오프 문서: `docs/handoff/handoff-{date}-{slug}.md`
브랜치: {브랜치명}
남은 작업: {핵심 1~2줄}
```

## 수신 (새 세션에서)

다음 세션 시작 시 memory에서 핸드오프 존재를 인지하면:

1. 핸드오프 문서를 읽는다
2. 사용자에게 물어본다: "이전 핸드오프를 이어할까요, 새로 시작할까요?"
3. 이어하면 → 문서의 "즉시" 항목부터 진행
4. 새로 시작하면 → 무시하고 진행

## 필수 규칙

1. **핸드오프 문서는 다음 세션의 AI가 읽는 문서**다 — 구체적 파일 경로, 커밋 해시, 브랜치명을 명시한다
2. **경량 유지** — 회고하지 않는다. 핸드오프는 빠른 바톤 터치
3. **대화 컨텍스트에서 추출할 수 없는 "남은 것"이 있으면** 사용자에게 확인한다
4. **AI가 임의로 발동하지 않는다** — 사용자가 `/handoff`를 명시적으로 입력했을 때만 실행
5. **검증되지 않은 것을 "완료"로 적지 않는다** — 빌드를 돌리지 않았으면 "미확인"이라고 쓴다. 다음 세션이 통과로 믿고 그 위에 쌓으면 원인 추적이 두 배로 어려워진다
