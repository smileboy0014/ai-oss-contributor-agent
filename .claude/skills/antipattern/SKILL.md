# Antipattern

## 핵심 원칙

**메모리는 잊는다. 하네스는 잊지 않는다.**

사용자가 "이거 하지 마"라고 말했을 때:
- 메모리에 기록 → LLM이 다음 세션에서 떠올리길 바람 (불안정, ~50%)
- 훅에 규칙 추가 → 다음에 시도하면 즉시 차단 (확실, 100%)

이 스킬은 안티패턴을 **훅 규칙 또는 스킬 체크리스트로 변환**하는 파이프라인이다.

> 🔴 이 프로젝트에서 특히 중요한 이유 — 여기서 만드는 것은 **남의 저장소에 코드를 밀어 넣을 수 있는 자동화**다.
> 평범한 버그는 우리 서비스가 죽지만, 안전 경계 위반은 **외부 OSS 커뮤니티로 직접 나간다.**
> 「다음엔 조심하자」로 끝내면 안 되는 종류의 실수가 많다.

## 사용법

```
/antipattern                          # 최근 세션에서 안티패턴 탐색
/antipattern <안티패턴 설명>            # 특정 안티패턴 지정
/antipattern --list                   # 현재 등록된 안티패턴 목록 확인
```

## 입력

안티패턴은 다양한 형태로 들어온다:

1. **사용자 피드백**: "이거 하지 마", "이건 위반이야"
2. **코드리뷰**: 리뷰어가 거부한 패턴
3. **세션 중 발견**: 구현 중 잘못된 방향을 나중에 수정한 경우
4. **직접 요청**: "이 패턴을 훅으로 막아줘"

## Step 1: 안티패턴 식별

사용자가 지적한 것 또는 대화에서 드러난 안티패턴을 구체적으로 정의한다.

```
안티패턴: [이름]
위반 코드: [구체적 코드 패턴]
올바른 대안: [어떻게 해야 하는지]
탐지 가능성: 정적 / 맥락 필요
안전 경계: [S-? 또는 해당 없음]
```

## Step 2: 분류 — 훅 vs 스킬 체크리스트

| 탐지 가능성 | 조치 |
|------------|------|
| **정적 탐지 가능** — 텍스트 패턴으로 잡힘 | → `.claude/scripts/` 훅 스크립트에 규칙 추가 |
| **맥락 판단 필요** — 파일 간 관계, 호출 그래프, 용도 이해 필요 | → 관련 스킬의 체크리스트에 추가 |
| **양쪽 다** | → 훅 + 체크리스트 모두 |

**판단 기준**: "이 패턴이 코드에 나타나면 100% 위반인가?" → Yes면 훅, No면 체크리스트.

## Step 3: 훅 규칙 작성 (정적 탐지 가능한 경우)

기존 스크립트에 규칙을 추가하는 것이 우선이다. 새 스크립트는 기존 것에 안 맞을 때만 만든다.

| 스크립트 | 담당 |
|---|---|
| [`safety-boundary-check.sh`](../../scripts/safety-boundary-check.sh) | S-1~S-4의 정적 탐지 가능분 (`git commit` 시점 **차단**) |
| [`secret-scan.sh`](../../scripts/secret-scan.sh) | 토큰 패턴 · `.env` 실값 (`git commit` 시점 **차단**) |
| [`impl-test-loop.sh`](../../scripts/impl-test-loop.sh) | Stop 시점 테스트 (차단 아님) |

🔴 **차단형은 `settings.json` 이 아니라 git 훅에 등록한다.** 앞의 둘은
[`.githooks/pre-commit`](../../../.githooks/pre-commit) 이 부르고, CI 가 `SCAN_MODE=tree` 로 다시 돈다.
`settings.json` 의 `PreToolUse` 에만 걸면 **사람이 직접 커밋하는 경로가 통째로 빠진다** —
실제로 그랬다([`hooks.md`](../../docs/hooks.md)). 피드백형(차단하지 않는 것)만 `settings.json` 에 둔다.

**규칙 작성 원칙:**
- 검사 대상 파일 범위를 명확히 (`src/**/*.java` 등)
- **false positive 최소화** — 너무 넓으면 개발이 멈춘다. 주석 라인·테스트 파일 제외를 먼저 고려
- 에러 메시지에 **조항 번호 + 왜 위험한지 + 올바른 대안**을 안내
- 의도된 예외는 `// safety-ok: <사유>` 로 통과시키되, **사유 없는 `safety-ok`는 통과시키지 않는다**

### 등록 — 차단형이면 git 훅

`.claude/scripts/` 에 규칙을 추가하는 것으로 끝나는 경우가 대부분이다.
두 스크립트는 이미 [`.githooks/pre-commit`](../../../.githooks/pre-commit) 에 걸려 있다.

새 **차단형** 스크립트를 만들었다면 그 훅에 한 줄 추가한다.

```bash
for script in secret-scan safety-boundary-check my-new-check; do
```

⚠️ `SCAN_MODE` 규약을 지킨다 — `staged`(기본, 훅)와 `tree`(CI)를 모두 지원하고,
**검사 대상이 0건이면 「실행하지 않았다」를 출력**한다. 조용한 통과는 게이트를 죽인다.

새 **피드백형**(차단하지 않는 것)은 [`settings.json`](../../settings.json) 의 `hooks` 에 등록한다.

## Step 4: 스킬 체크리스트 추가 (맥락 판단 필요한 경우)

관련 스킬의 체크리스트에 항목을 추가한다. `/improve-skill`과 연계.

주 대상: [`pr-review`](../pr-review/SKILL.md) 체크리스트, [`plan`](../plan/SKILL.md) 리스크 평가, [`work`](../work/SKILL.md) Phase 게이트.

## 훅 승격 후보

`👁` 중 grep으로 충분히 잡히는 것은 훅으로 승격한다. 현재 후보:

| 항목 | 승격 방법 |
|---|---|
| #17 `Instant.now()` | `src/main/java/**` 에서 `Instant.now()` grep. 테스트·`ClockConfig` 제외 |
| #14 domain 에 Spring import | `src/main/java/com/ossagent/*/domain/**` 에서 `import org.springframework` grep (JPA 는 `jakarta.persistence` 라 무관) |
| #20 `client`·`port` 패키지명 | 디렉토리명 검사 |
| #16 남의 도메인 import | 경로의 도메인명과 import 의 도메인명 비교 |

**승격 판단 기준**: 오탐이 거의 없고, 위반이 실제로 관찰된 것부터. 아직 한 번도 발생하지 않은 것을 미리 훅으로 만들면 개발 흐름만 막는다.

## 훅 확장 시 주의사항

- **false positive 최소화**: 규칙이 너무 넓으면 개발 흐름이 멈춘다. 의심스러우면 체크리스트에 먼저 두고, 패턴이 명확해지면 훅으로 승격
- **에러 메시지가 곧 문서**: "왜 안 되는지"와 "대신 뭘 써야 하는지"를 명확히. 조항 번호(S-?)를 반드시 포함
- **제외 범위**: 테스트 파일(`src/test/**`), 주석 라인은 대부분의 규칙에서 제외
- **훅 통과가 합격이 아니다**: 훅은 문자열만 본다. 호출 그래프를 따라가야 아는 위반은 잡히지 않는다 — 판단은 리뷰와 사람이 한다
