# PRD

"무엇을 왜 하는가"를 개발자 관점에서 정의하는 정책 요구사항 문서를 생성합니다. 구체적 기술 구현 방법은 `/plan`에 위임합니다.

## 문서 목적 및 대상

### 목적

- **정책 기술서**: 파이프라인 전체 흐름을 이해할 수 있는 기능 및 동작 정책을 정밀하게 기술한 가이드

### 대상

| 대상 | 전제 | PRD로 할 수 있는 것 |
|------|------|---------------------|
| 구현자 | 코드베이스 이해도 있음 | 동작 정책과 안전 경계 파악 |
| 리뷰어 | 코드베이스 모름 | 정책 의도를 정확히 파악하고 리뷰 기준 확보 |

## 사용 시점

- 새로운 파이프라인 단계 개발 시작 전
- 기존 단계의 대규모 개선/변경 전
- 안전 경계에 닿는 변경을 착수하기 전

## 사용법

```
/prd                    # 대화형 PRD 생성 시작
/prd <기능 설명>          # 기능 설명으로 PRD 생성 시작
```

## 워크플로우

```
/prd → 질의응답 → PRD 초안 생성 → 검토/수정 → 최종 저장
                                          ↓
                                    /plan 연계 (선택)
```

## 동작 방식

### Phase 1: 정보 수집

사용자의 자연어 설명을 받은 후, 다음 영역에 대해 체계적으로 질의합니다.

#### 1.1 기본 정보 수집

| 질의 항목 | 목적 |
|----------|------|
| 기능 명칭 | PRD 제목 및 파일명 결정 |
| 배경/문제 정의 | 왜 이 기능이 필요한지 |
| 목표 | 달성하고자 하는 구체적 결과 |
| 성공 지표 | 기능 성공 여부를 판단할 기준 |
| 범위 (In/Out) | 포함/제외 항목 명확화 |

#### 1.2 정책/도메인 정보 수집

| 질의 항목 | 목적 |
|----------|------|
| 비즈니스 규칙 | 도메인 로직, 판정 기준 |
| 수용 기준 | 기능이 "완료"로 인정되는 조건 |
| 엣지케이스 정책 | 예외 상황에 대한 처리 방침 |
| 의존 정책 | 기존 정책과의 관계, 영향 범위 |

#### 1.3 OSS 에이전트 도메인 정보 수집 (해당 시)

| 질의 항목 | 목적 |
|----------|------|
| 대상 도메인 | `repository` / `issue` / `candidate` / `agent` / `pullrequest` / 공통 |
| 후보 상태 전이 | `DISCOVERED`·`ANALYZING`·`ANALYZED`·`SELECTED`·`IMPLEMENTING`·`TESTING`·`REVIEWING`·`READY_FOR_PR`·`PR_CREATED`·`REJECTED`·`FAILED` 중 관련 전이 |
| 외부 경계 | GitHub API(조회·Fork·push·Draft PR) / LLM API(분석·계획·코딩·리뷰) / Docker 샌드박스(빌드·테스트) |
| 멱등 & 재시도 | 스캔 재실행 멱등 · `agent.execution.max-retries` 소진 조건 · 재시도 카운터 단위 |
| **안전 경계 접촉** | **S-1~S-6 중 어디에 닿는가** — 닿으면 해당 조항을 FR·수용 기준에 명시 |
| 대상 저장소 규약 영향 | `RepositoryPolicy`(sign-off·이슈 참조·테스트 필수·AI 기여 허용 여부)를 바꾸거나 소비하는가 |
| 비용·레이트리밋 | GitHub 레이트리밋 · LLM 토큰 소비에 영향이 있는가 |

> **참고**: 용어는 [`glossary.md`](../../rules/context/glossary.md), 안전 경계는 [`safety-boundaries.md`](../../rules/context/safety-boundaries.md), 상태머신은 [`domain.md`](../../codemaps/domain.md), 데이터는 [`data.md`](../../codemaps/data.md).
> **미결 확인 필수**: [`open-questions.md`](../../rules/context/open-questions.md)에 걸린 항목(Q-1~Q-10)은 **추측으로 채우지 말고 확인**한다. 확인이 불가능하면 가정을 명시하고 진행한 뒤 PRD에 그 가정을 남긴다.

### Phase 2: PRD 초안 생성

수집된 정보를 바탕으로 PRD 초안을 생성합니다.

### Phase 3: 검토 및 수정

- 초안을 사용자에게 제시
- 피드백 반영하여 수정
- 누락된 항목 보완

### Phase 4: 최종 저장

```
docs/prd/PRD-{issue}.md
```

`{issue}`는 GitHub 이슈 번호다. 이슈가 없으면 슬러그를 쓴다 (`PRD-github-issue-scanner.md`).

## PRD 템플릿

### 문서 헤더

    # PRD: {기능명}
    **Issue**: [#{issue}](https://github.com/smileboy0014/ai-oss-contributor-agent/issues/{issue}) (해당 시)

### 섹션 구성

| 섹션 | 필수 | 내용 |
|------|------|------|
| 1. 개요 | ✅ | 배경, 목표, 성공 지표 |
| 2. 범위 | ✅ | In/Out Scope, 가정/제약사항 |
| 3. 요구사항 | ✅ | 기능(FR), 비기능(NFR) 요구사항 |
| 4. 수용 기준 | ✅ | 기능별 완료 조건, 검증 시나리오 |
| 5. 도메인 규칙 | ✅ | 비즈니스 로직, 판정 기준, 엣지케이스 처리 방침 |
| 6. OSS 에이전트 도메인 명세 | 조건부 | 대상 도메인, 상태 전이, 외부 경계, 멱등·재시도, **안전 경계**, 대상 저장소 규약 영향 |
| 7. 운영 명세 | 조건부 | 레이트리밋·토큰 비용·타임아웃·관측 지표 |
| 8. 의존성 | ✅ | 내부/외부 의존, 영향 범위 |
| 9. 리스크 및 대응 | ✅ | 리스크, 영향도, 대응 방안 |
| 10. 참고 자료 | 선택 | 관련 문서, 원본 PRD 절 번호 |
| 11. 변경 이력 | ✅ | 일자, 작성자(GitHub username), 변경 내용 |

**작성자 결정**: GitHub username을 사용합니다. `git config user.name`이 아닌 GitHub 계정명 기준입니다.

상세 템플릿은 [`references/template.md`](./references/template.md).

### 3. 요구사항 — FR 작성 원칙

FR은 PRD의 핵심 섹션입니다. 다음 원칙을 반드시 준수합니다:

#### 코드 참조 금지

FR에 변수명, 함수명, 파일 경로, 코드 표현식을 포함하지 않습니다. 코드 수준의 구현 상세는 `/plan`의 "FR 구현 상세" 섹션에서 다룹니다.

```markdown
# ❌ 잘못된 예시 (코드 혼재)
| FR-3.1 | `DockerCodeSandbox.execute()` 에서 `SANDBOX_TIMEOUT_SECONDS` 초과 시 `container.kill()` 후 `AgentRun.status = TIMEOUT` 으로 갱신 |

# ✅ 올바른 예시 (정책 언어, 구현 가능한 정밀도)
| FR-3.1 | 샌드박스 실행이 제한 시간을 초과하면 컨테이너를 강제 종료하고, 해당 실행을 타임아웃 실패로 기록한다. 종료에 실패해도 실행 기록은 남긴다 [S-3] |
```

#### 구현 가능한 정밀도

코드 참조 없이도 **이 문서만 읽고 구현할 수 있는 수준**으로 정밀하게 기술합니다.

#### 안전 경계 인용

안전 경계에 근거한 요구사항은 **조항 코드를 남깁니다.** 경계 문서가 개정돼도 어디를 다시 볼지 특정됩니다.

```markdown
| FR-2.3 | push 대상 원격의 소유자가 설정된 Fork 소유자와 일치하지 않으면 push 를 수행하지 않고 실행을 중단한다 [S-1] |
| FR-4.1 | 생성하는 Pull Request 는 언제나 draft 상태이며, draft 를 해제하는 경로를 제공하지 않는다 [S-2] |
```

#### 동작 예시 포함

복잡한 FR에는 구체적인 동작 예시를 포함하여 정책 의도를 명확히 합니다.

### 3/4/5 섹션 역할 구분

| 섹션 | 역할 | 관점 |
|------|------|------|
| **FR (요구사항)** | 무엇을 해야 하는가 | 기능 명세 |
| **수용 기준** | 어떻게 확인하는가 | 검증 조건 |
| **도메인 규칙** | 왜 이렇게 하는가 | 비즈니스 원칙 |

### 4. 수용 기준 상세

```markdown
#### FR-1: {요구사항명}
- [ ] {조건 A}일 때 {결과 B}가 발생한다
- [ ] {조건 C}일 때 {결과 D}가 발생하지 않는다
- [ ] 엣지케이스: {상황}에서 {처리 방침}
```

### 5. 도메인 규칙 상세

```markdown
#### 규칙 1: {규칙명}
- 기준: {판단 기준}
- 정책: {처리 방침}
- 예외: {예외 상황과 대응}
```

## 질의 프로세스

### 필수 질의 (모든 PRD)

다음 정보가 누락된 경우 반드시 질의합니다:

1. 기능의 배경과 목적이 무엇인가요?
2. 이 기능의 성공을 어떻게 측정할 수 있나요?
3. 범위에서 명확히 제외해야 할 것이 있나요?
4. 각 요구사항의 수용 기준(완료 조건)은 무엇인가요?
5. 예외 상황이나 엣지케이스에 대한 처리 방침이 있나요?

### 조건부 질의 (해당 시)

**파이프라인 단계와 관련된 기능인 경우:**
- 어느 도메인인가요? (`repository` / `issue` / `candidate` / `agent` / `pullrequest` / 공통)
- 후보 상태 전이에 영향이 있나요? (분석 / 선정 / 구현 / 검증 / 리뷰 / PR 생성 / 실패)
- 외부 경계를 넘나요? (GitHub API / LLM API / Docker 샌드박스)
- 멱등이 필요한가요? (스캔 재실행 / 재시도 카운터)
- **안전 경계에 닿나요?** (S-1 Fork 외 쓰기 / S-2 draft·머지 / S-3 샌드박스 / S-4 시크릿 / S-5 대상 저장소 규약 / S-6 승인 지점)
- 대상 저장소의 기여 규약을 읽거나 바꾸나요?

**비용·부하에 영향이 있는 경우:**
- GitHub 레이트리밋 소비가 늘어나나요?
- LLM 토큰 소비가 늘어나나요? 어느 단계에서요?
- 샌드박스 실행 횟수·시간이 늘어나나요?

### 선택 질의 (상세화 필요 시)

- 기존에 참고할 만한 유사 단계가 있나요?
- 특별히 고려해야 할 엣지 케이스가 있나요?
- 성능 요구사항이 있나요?

## 저장 및 연계

### 파일 저장

```
docs/prd/PRD-{issue}.md
```

**저장 완료 알림:**

    PRD가 생성되었습니다: docs/prd/PRD-{issue}.md

    다음 단계:
    1. /plan - 구현 계획 수립

### /plan 연계

PRD 승인 후 `/plan` 커맨드와 연계하여 구현 계획을 수립할 수 있습니다:

- `docs/prd/PRD-{issue}.md` 참조
- 요구사항/수용 기준 기반 구현 단계 도출
- 도메인 규칙 기반 기술 설계
- **FR 구현 상세**: PRD 정책 → 코드 수준 매핑

## 필수 규칙

1. **질의 우선**: 정보가 불충분하면 가정하지 말고 질의합니다.
2. **코드 참조 금지**: FR에 변수명, 함수명, 파일 경로, 코드 표현식을 포함하지 않습니다.
3. **구현 가능한 정밀도**: 이 문서만 읽고 구현할 수 있는 수준으로 정밀하게 기술합니다.
4. **수용 기준 필수**: 모든 기능 요구사항에 대해 완료 조건을 명시합니다.
5. **안전 경계 명시**: S-1~S-6에 닿는 요구사항은 조항 코드를 인용하고, 수용 기준에 "어기지 않았음"을 검증하는 항목을 넣습니다.
6. **범위 명확화**: In/Out Scope를 명확히 구분합니다. **Non-Goal은 "나중에 할 것"이 아니라 "하지 않을 것"입니다.**
7. **증분 작성**: 초안 → 검토 → 수정 사이클을 거칩니다.
8. **기술 구현 위임**: API 설계, 데이터 모델, 상태 설계 등 기술 상세는 `/plan`에서 다룹니다.

## 연계 커맨드

- `/plan` — PRD 기반 구현 계획 수립
- `/work` — 티켓 lifecycle 안에서 자동 호출
- `/discuss` — PRD 이전 요구사항 정제
