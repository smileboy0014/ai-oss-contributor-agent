## 1. 🔴 착수 전 필수 — 누적 회귀 기준선

이슈가 「`TokenRedactor` 를 만지기 전에 누적 프로브를 먼저 돌린다」를 요구했다.

```
./gradlew test --tests *TokenRedactorTest* --tests *SecretPatternDriftTest* --tests *SecretScanScriptTest*
exit=0 · > Task :test (접미사 없음) · 실패 0 · 86 케이스

```

⚠️ 처음에 「23 케이스」로 적었다 — **`@Test` 애노테이션을 센 것**이라 파라미터라이즈드
케이스가 빠졌다. 요구 0(「돌기는 하는가」)의 증거로 적는 숫자가 실행과 달랐다.

1~6차에서 닫은 것이 열려 있지 않다.

## 2. ② `shapeOf` 단순화 — 🔴 **측정했고, 채택하지 않는다**

### 무엇을 바꾸려 했나

장식 계산을 **「전체 길이 − 런」 → 「런 밖의 비공백 문자 수」**로 바꾸면 들여쓰기·줄 안쪽
공백이 예산을 쓰지 않아 `decorationBudget` 을 **삭제**할 수 있다. #28 6차 리뷰가
「전체 프로브로 회귀 0건」을 측정해 뒀고, 나도 이 브랜치에서 **재현**했다.

```
누적 회귀(TokenRedactorTest · SecretPatternDriftTest) → exit=0 · 실패 0
```

### 🔴 그런데 「회귀 0건」이 「안전」이 아니었다 — 새 모양을 찾았다

`shapeOf` javadoc 이 이미 경고하고 있었다.

> ⚠️ 줄 안쪽 공백은 그대로 센다 — **그것을 빼면 영문 산문이 본문으로 먹힌다**

누적 스위트에 **그 모양이 없어서** 0건이 나왔을 뿐이다. 이슈 본문이 경계한
「프로브는 생각해 낸 모양만 본다」가 정확히 이 자리다.

**과차단 프로브 3건을 새로 만들어 전후를 쟀다.**

| 프로브 | 기준선 | ② 적용 |
|---|---|---|
| 마크다운 표 행 `\| x \| <64자 해시> \|` | 🔴 **이미 소실** | 🔴 소실 |
| 공백 많은 설명줄 `sha : <해시>  (배포 태그)` | ✅ 살아남음 | ✅ 살아남음 |
| **들여쓴 표 행** `  \| id \| <해시> \| ok \|` | ✅ 살아남음 | 🔴 **새로 소실** |
| **합계** | **1/3 과차단** | **2/3 과차단** |

들여쓴 표 행은 `|` 주변 공백이 예산을 넘겨 진입을 막고 있었는데, 공백을 세지 않으면
비공백 장식이 4 ≤ 8 이 되어 **진입하고 그 뒤가 통째로 먹힌다.**

### 확정 — 하지 않는다

**①을 거부한 근거가 ②에도 그대로 적용된다.** 소실된 값은 `IssueSnapshot` 을 통해
**DB 에 영속되고 원문 복구 경로가 없다.** 얻는 것은 **메서드 하나의 삭제**뿐이다.

⚠️ 「그럼 예산을 올리면 되지 않나」 — `BASE_DECORATION_BUDGET` 을 낮추면 이번엔
**키 쪽이 샌다**(`decorationBudget` javadoc: 「상수 8 로 두었더니 들여쓰기 9칸부터 키가 샜다」).
**두 방향이 같은 손잡이 하나에 남아 있다**는 이슈 본문의 진단이 여기서도 그대로다.

### 🔴 측정을 테스트로 고정한다

문서에만 적으면 다음 사람이 같은 단순화를 다시 시도한다 — **#28 6차 측정이 「회귀 0건」이라
적혀 있는 한 그것은 유혹으로 남는다.**

| 하는 것 | |
|---|---|
| `들여쓴 표 행` 프로브를 **회귀 테스트로 남긴다** | 지금 초록이고, ②를 적용하면 **빨개진다** |
| `공백 많은 설명줄` 도 남긴다 | 같은 축의 양성 대조 |
| `마크다운 표 행` 은 **테스트로 만들지 않는다** | 🔴 **지금도 실패한다** — 새로 찾은 F-3 사례다. 이슈에 기록한다 |

### 돌연변이 — 「무엇을 빼니 몇 건이 빨개졌다」

`testing-philosophy` 가 「돌연변이를 돌려 봤다」가 아니라 **숫자**를 요구한다.

| 무엇을 했나 | 결과 |
|---|---|
| ② 적용(`shapeOf` 비공백 기준 + `decorationBudget` 삭제) | 🔴 **1건 적색** — `들여쓴_표_행은_먹히지_않는다_S4` |
| ① 후보 축(`headerOwnsItsLine`) 적용 | 🔴 **1건 적색** — `장식이_더_붙은_키_본문 [3] 번호 목록`(65건 중) |
| ③ 을 흘러내림으로 되돌림 | ✅ **0건** — 동작 변화 0 확인(의도대로) |

⚠️ 세 줄의 뜻이 서로 다르다 — 위 둘은 **가드가 문다**는 증거이고, 마지막 줄은
**동작이 같다**는 증거다. 마지막 줄을 「가드가 없다」로 읽지 않는다.

## 3. ① F-3 과차단 — 🔴 **측정했고, 채택하지 않는다**

### 무엇이 문제인가

산문에서 PEM 헤더를 **언급**만 해도 뒤 20줄 안의 긴 키 문자 런이 소실된다.

```
이 헤더를 커밋하지 마세요: -----BEGIN RSA PRIVATE KEY-----
(빈 줄 몇 개)
src/main/java/com/ossagent/support/secret/TokenRedactor.java   ← 여기까지 소실
```

파일 경로는 `/` 가 키 문자라 런이 55다. 소실된 값은 `IssueSnapshot` 을 통해 **DB 에
영속되고 원문 복구 경로가 없다.**

### 후보 축과 그 측정

이슈가 든 후보 축 — **「헤더가 제 줄을 통째로 차지했는가」**.
산문 속 언급이면 공격적 진입을 하지 않는다.

```java
headerOwnsItsLine(text, headerStart)   // 헤더 앞이 장식뿐인가
    ? endOfKeyBlock(...)               // 제 줄을 차지했다 — 지금처럼
    : lineEnd(text, header.end());     // 산문 속 언급 — 헤더 줄만 가린다
```

**결과 — 유출이 늘어난다.**

```
TokenRedactorTest  65 tests completed, 1 failed
FAILED: 장식이_더_붙은_키_본문 [3] 번호 목록
```

`1. -----BEGIN RSA PRIVATE KEY-----` 처럼 **번호 목록 안에 있는 진짜 키**가
「제 줄을 차지하지 않았다」로 판정돼 **본문이 통째로 샌다.** 그 테스트는
`doesNotContain(body)` 로 「실제 키가 가려진다」를 단언하고 있다.

⚠️ 장식 목록에 `1.` 을 넣으면 그 케이스는 통과하지만, **그것이 바로 #28 이 세 번 연속
실패한 거부목록 방식**이다 — 「목록에 없는 형태마다 구멍이 새로 난다」.
`testing-philosophy` 가 「같은 구멍이 세 번 반복되면 패치가 아니라 축을 의심한다」로
규약에 올려 둔 그 자리이고, 여기서 목록을 늘리는 것은 그 규약을 **정면으로** 어기는 것이다.

### 확정

**채택하지 않는다.** 이슈의 완료 조건이 「새 축이 유출을 늘리지 않는다는 것을 **측정으로**
보인 경우에만」이었고, 측정 결과가 **정반대**다.

🔴 **그래서 이슈를 닫지 않는다** — 이슈 자신이 「못 보이면 닫지 말고 근거를 남긴다」고 정했다.
측정 결과를 그 이슈에 남긴다.

⚠️ 남은 손실의 크기를 다시 적어 둔다 — 조건이 「PEM 헤더 문자열 등장」 **AND**
「20줄 안에 40자 런 등장」 둘 다여서, 3차에 닫은 C-2(어떤 한 단어 줄이든 소실)보다
**두 자릿수 좁다.** 반대편에 있는 것은 **진짜 키의 유출**이다.

## 4. ③ 분기 대칭성 — 동작 변화 0

`endOfKeyBlock` 의 `probed` 분기가 거짓이면 `else { return beforeWindow; }` 로 **흘러내린다.**
그것이 마침 원하던 동작이라 버그가 아니다 — **다만 우연이다.**

```java
// 지금 — 조건이 거짓이면 아래 else 로 흘러내린다
} else if (continuesKeyBody(line, budget) && ++probed <= ENTRY_WINDOW_LINES) {
} else {
    return beforeWindow;
}

// 바꾼 뒤 — passesThroughToEntry 와 같은 모양으로 분기 안에서 끝낸다
} else if (continuesKeyBody(line, budget)) {
    if (++probed > ENTRY_WINDOW_LINES) {
        return beforeWindow;
    }
} else {
    return beforeWindow;
}
```

⚠️ #28 에서 **정확히 이 실수를 한 번 했다** — `&& ++passed <= LIMIT` 로 붙였더니 조건이
거짓이 되는 순간 다음 분기로 흘러내려 같은 줄을 두 번 판정했고 테스트 3건이 빨간 채였다.
그 경험이 바로 위 `passesThroughToEntry` 분기에 주석으로 남아 있다.

🔴 **동작이 같다는 것을 테스트가 아니라 논증으로 보인다** — 두 경로 모두 `beforeWindow` 를
돌려주므로 관측 가능한 차이가 없다. 그래서 새 테스트를 만들지 않는다.
**동작이 같은 변경에 테스트를 붙이면 그 테스트는 아무것도 막지 못한다.**
