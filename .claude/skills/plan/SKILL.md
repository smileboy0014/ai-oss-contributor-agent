# 구현 계획 수립

요구사항을 분석하여 코드 레벨의 구현 계획을 작성합니다.

## 입력

- GitHub 이슈, PRD, 또는 자연어 요구사항
- `$ARGUMENTS`: 이슈 번호 또는 추가 컨텍스트

## 스코프 판단

플랜을 시작하기 전에 변경이 **어느 도메인에 속하는지** 판단한다. 참조된 파일 경로와 요구사항 키워드를 근거로 분류한다.

| 도메인 | 신호 | 소유 |
|---|---|---|
| `repository` | 대상 저장소 등록·조회, 기여 규약, `RepositoryPolicy` | 어떤 저장소를 보고 있고 그 규약이 무엇인가 |
| `issue` | 이슈 수집, 필터, 스캔 커서, 레이트리밋 | 어떤 이슈가 있고 무엇이 후보 자격이 있는가 |
| `candidate` | 상태머신, 후보 선정, 분석 결과 저장 | 이 이슈가 기여 가능한가 · 지금 어느 단계인가 |
| `agent` | LLM 호출, 구현 계획 생성, 코드 생성, 샌드박스, 재시도, 토큰·비용 | 실행 이력과 비용 |
| `pullrequest` | Fork, 브랜치 push, Draft PR, PR 템플릿 | Fork·브랜치·PR 메타데이터 |
| `support` / `config` | 예외 매핑, 공통 클라이언트, 빈 조립 | 도메인 없는 공통 |
| **여러 도메인** | 파이프라인 단계를 가로지름 | 아래 「여러 도메인」 절 참조 |

**여러 도메인에 걸치면** — 도메인 간 인터페이스(능력 인터페이스 또는 UseCase 공개 메서드)를 **먼저 확정**하고, 그 계약을 계획서 맨 앞에 적는다. 계약이 흔들리면 양쪽 구현이 함께 흔들린다.

## 프로세스

### 1. 컨텍스트 수집

1. **[`safety-boundaries.md`](../../rules/context/safety-boundaries.md) 를 먼저 읽는다** — 이 작업이 S-1~S-6 중 무엇에 닿는가
2. **[`open-questions.md`](../../rules/context/open-questions.md) 를 읽는다** — 이 영역이 확정됐는지. 미결이면 계획 대신 확인 요청
3. [`codemaps/`](../../codemaps/) (architecture·data·domain) 읽어 구조 파악
4. [`rules/context/`](../../rules/context/) (project-overview·glossary·external-deps) 읽어 도메인·용어 확인
5. [`rules/conventions/architecture.md`](../../rules/conventions/architecture.md) 로 레이어 배치 규율 확인
6. 관련 기존 코드 탐색

### 2. 요구사항 분석

1. 기능 요구사항(FR) 도출
2. 비기능 요구사항(NFR) 식별 — 레이트리밋, 타임아웃, 비용, 동시성
3. 영향 범위 파악 (어떤 도메인/패키지에 영향?)

### 3. 기술 설계

공통:
1. 변경/생성할 파일 목록
2. 각 파일의 변경 내용 상세 기술
3. API 엔드포인트 & 계약 (요청/응답) — 해당 시
4. 데이터 모델 / 타입 정의

**이 프로젝트 필수 체크리스트** — 항목마다 답을 계획서에 적는다. 「해당 없음」도 답이다.

| # | 항목 | 왜 |
|---|------|---|
| 1 | **소유 도메인 판정** — 이 데이터·행위를 누가 소유하는가 | 두 도메인이 같은 것을 소유하면 나중에 못 가른다 |
| 2 | **헥사고날 레이어 배치** — domain / application / adapter 중 어디에 두는가 | 판단은 [`architecture.md`](../../rules/conventions/architecture.md) §3 의 Q1~Q5 결정 트리로 |
| 3 | **능력 인터페이스가 필요한가** — 필요하면 **능력 이름**으로 domain 에 선언 (`IssueSource`·`CodeSandbox`·`DraftPrPublisher`), 구현은 **기술 이름**으로 adapter/out (`GitHubIssueSource`·`DockerCodeSandbox`) | `client`·`port` 라는 이름을 쓰면 기술이 domain 으로 새어 들어온다 |
| 4 | 🔴 **트랜잭션 안에 대외 호출이 없는가** | 샌드박스 실행은 최대 30분이다. 트랜잭션에 들어가면 커넥션이 30분 잡힌다. GitHub·LLM 도 동일 |
| 5 | **상태 전이 영향** — `CandidateStatus` 전이를 추가·변경하는가 | 종단 상태(`PR_CREATED`·`REJECTED`·`FAILED`)에서 나가는 전이를 만들지 않는다 |
| 6 | **멱등성** — 스캔 재실행·재시도·이벤트 재수신에서 두 번 적용되지 않는가 | 중복 후보 생성·중복 PR 은 되돌리기 어렵다 |
| 7 | **`Clock` 주입** — 시각 판단이 있는가 | `Instant.now()` 직접 호출은 만료·타임아웃 경계를 테스트로 고정할 수 없게 만든다 |
| 8 | 🔴 **안전 경계 접촉 여부** — S-1~S-6 중 무엇에 닿는가, 어떻게 지키는가 | 아래 표 |

#### 안전 경계 대조표

| 조항 | 이 계획이 닿는가 | 닿으면 계획서에 적을 것 |
|---|---|---|
| **S-1** 원본 저장소 쓰기 금지 | push·remote·Fork 좌표를 다루는가 | push 대상이 Fork 임을 보장하는 **어설션의 위치** |
| **S-2** 항상 draft · 자동 머지 금지 | PR·리뷰·코멘트 API 를 호출하는가 | `draft: true` 고정 지점 · 머지/ready 호출이 없음을 명시 |
| **S-3** 샌드박스 밖 실행 금지 | 대상 저장소 코드를 빌드·테스트하는가 | 샌드박스 경유 경로 · 네트워크·CPU·메모리·타임아웃 제한 |
| **S-4** 시크릿 유출 금지 | 시크릿·LLM 프롬프트·로그를 다루는가 | 프롬프트 스크럽 지점 · 로그 마스킹 대상 |
| **S-5** 대상 저장소 규약 우선 | 대상 저장소에 나가는 산출물을 만드는가 | `RepositoryPolicy` 를 읽는 지점 · 규약 미확인 시 보류 처리 |
| **S-6** 승인 지점 우회 금지 | 상태 전이·재시도·스케줄을 다루는가 | 사람 승인 지점 · 재시도 상한이 살아 있음 |

### 4. 의존성 & 순서

1. 파일 간 의존성 그래프
2. 구현 단계(Stage) 분리
3. 각 단계의 선행 조건 명시

### 5. 실행 전략 결정

작업의 특성과 파일 의존성을 분석하여 최적의 실행 전략을 결정합니다.

#### 5.1 작업 유형 분류

| 유형 | 설명 | 기본 전략 |
|------|------|----------|
| `multi-domain-creation` | 독립된 도메인 N개에 각각 추가 | parallel |
| `independent-bug-fixes` | 서로 무관한 버그 N개 수정 | parallel |
| `file-split-refactor` | 하나의 파일을 여러 단위로 분리 | sequential |
| `contract-and-impl` | 능력 인터페이스 신설 + 구현 | sequential |
| `mixed` | 위 유형이 혼합된 경우 | phased |

#### 5.2 의존성 분석

각 구현 단계의 수정 파일을 Create/Modify/Delete 로 구분하고, 단계 간 파일 겹침과 import 의존 방향을 분석합니다.

**병렬 가능 조건 (모두 충족해야 함):**
- 수정(Modify) 파일이 단계 간 겹치지 않음
- 한 단계의 산출물을 다른 단계가 import 하지 않음

#### 5.3 실행 모드 판정

| 모드 | 조건 | 동작 |
|------|------|------|
| `sequential` | 유형이 순차 적합 또는 파일 겹침 있음 | 기존 방식 그대로 |
| `parallel` | 모든 단계가 독립적 + 유형이 병렬 적합 | 전체 병렬 |
| `phased` | 일부 단계만 병렬 가능 | Phase 그룹별 순차/병렬 혼합 |

### 6. 리스크 평가

1. 기존 기능에 영향 가능한 부분
2. 🔴 **안전 경계** — 위 대조표에서 닿은 조항. 어기면 외부 OSS 커뮤니티에 사고가 직접 나간다
3. **대외 호출 실패 시나리오** — GitHub 레이트리밋(403 로 오는 2차 리밋 포함) · LLM 타임아웃 · 샌드박스 OOM
4. **비용** — LLM 토큰이 재시도 루프에서 몇 배가 되는가
5. 성능 영향

### 7. 복잡도 추정

| 단계 | 파일 수 | 복잡도 |
|------|--------|--------|
| 1단계 | N | 낮음/중간/높음 |

## 출력 형식

계획서를 `docs/plans/PLAN-{issue}.md` 에 저장합니다. 이슈가 없으면 `docs/plans/PLAN-{slug}.md`.
템플릿은 [`references/template.md`](./references/template.md) 참조.

## PRD 연계

PRD 가 있는 경우 (`docs/prd/PRD-{issue}.md` 또는 루트 [`docs/ai-oss-contributor-agent-prd.md`](../../../docs/ai-oss-contributor-agent-prd.md)):
- PRD 의 FR 을 기반으로 구현 단계 도출
- FR 매핑 테이블에 PRD 의 FR 번호 또는 절 번호를 정확히 매핑

## 이후 단계

계획 확정 후 [`/work`](../work/SKILL.md) 의 Phase 2 로 단계별 구현을 시작합니다.

## 연계 커맨드

- `/prd` — PRD 기반으로 Plan 작성
- `/work` — 계획부터 PR 까지 lifecycle
- `/pr` — 구현 완료 후 PR 생성
