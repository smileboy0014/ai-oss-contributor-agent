## 1. 요구사항

### 배경

대외 의존이 셋(GitHub API · LLM API · Docker 샌드박스)인데 **전부 느리거나 비결정적**이다.
그대로 타는 테스트를 만들면 스위트가 죽는다 — 레이트리밋을 테스트가 태우고, 같은 입력에 같은
출력이 나오지 않고, 컨테이너 하나에 수 분이 걸린다.

[`testing-philosophy.md`](../../.claude/rules/conventions/testing-philosophy.md) 는 대체 수단을
**「미정 — 정해지기 전까지는 자체 페이크」**라는 잠정 규정으로 두고 Q-9 로 넘겨 뒀다.
이 작업이 그 잠정 규정을 **정식 확정**으로 바꾼다.

**지금 정해야 하는 이유** — 능력 인터페이스가 막 생기고 있다. 열려 있는
[PR #35](https://github.com/smileboy0014/ai-oss-contributor-agent/pull/35)(#6)이
`FakeIssueSource` · `FakeRepositorySource` 를 이미 만들었고, PR 본문이 그것을
**「Q-9 잠정 규정을 따른 가정」**이라고 명시하고 있다. #7 · #8 · #15 · #22 · #23 이
같은 계약 위에 올라오므로, 여기서 규약을 못 박지 않으면 페이크가 제각각 자란다.

### 이 계획이 「결정」과 「코드」를 함께 내는 이유

이슈 완료 조건 3번은 「`@SpringBootTest` 에서 **실제 어댑터가 올라오지 않는 것**을
보장하는 방법 결정」이다. **「보장」은 문서로 달성되지 않는다.** 규약만 적어 두면
다음 어댑터가 규약을 모른 채 컨텍스트에 올라오고, 그때 테스트가 조용히 네트워크를 탄다.
그래서 산출물에 **강제 장치(가드 테스트)**를 포함한다.

## 3. 결정 — Q-9 의 답

### 3.1 대역 층 — 병행 PR 의 3계층 + HTTP 가 아닌 두 경로

**HTTP 층 3개는 병행 작업(`docs/_open-questions-decisions`)이 확정한다.** 여기 옮겨 적는 이유는
아래 두 경로가 **그 3계층 어디에도 속하지 않기** 때문이다 — 빠뜨리면 S-1·S-3 의
커버리지 100% 시나리오를 쓸 수 없다.

| 층 | 대역 | 무엇을 보나 |
|---|---|---|
| 능력 소비자 (UseCase) | 자체 페이크 | 계약이 실제로 대체 가능한가 · 업무 흐름 |
| 어댑터 매핑 | `MockRestServiceServer` | 요청 조립 · 응답 파싱 · 403 구분 |
| 전송 계약 | **WireMock** | 읽기 타임아웃 · 리다이렉트 거부 · 연결 실패 |

⚠ **WireMock 이 세 번째 층에 필요한 이유** — `MockRestServiceServer` 는
`ClientHttpRequestFactory` 를 통째로 갈아끼우므로 **JDK `HttpClient` 가 아예 돌지 않는다.**
`read-timeout`·`Redirect.NEVER` 가 「프로퍼티에 값이 있다」까지만 확인되고 **실제로 걸리는지는
알 수 없다** — #35 가 「읽기 타임아웃 미검증」으로 스스로 남긴 한계가 이것이다.
초안이 WireMock 을 기각했던 것은 이 사실을 놓친 판단이었고, **철회한다.**

#### HTTP 가 아닌 두 경로 — 이 계획이 추가하는 것

| 경로 | 대역이 해야 할 일 | 조항 |
|---|---|---|
| **git 전송** (clone · branch · **push**) | 실제 원격이 아니라 **push 시도를 기록**한다. 「upstream 좌표면 중단 / Fork 좌표면 위임」을 원격 없이 검증 — 어설션은 순수 판정이다 | 🔴 **S-1** |
| **컨테이너 제어** (docker 호출) | 제어 호출을 기록해 **「timeout 후 remove 가 불렸는가」**를 본다 | 🔴 **S-3** |

「타임아웃 시 컨테이너가 정리된다」는 **능력 페이크로 증명되지 않는다** — 페이크는 컨테이너를
만들지 않는다. 층을 하나 더 두는 이유가 이것이다.

🔴 **실제 대외 시스템을 타는 자동 테스트를 만들지 않는다** — GitHub(REST·git) · LLM · Docker 컨테이너.
E2E 는 `testing-philosophy.md` 가 이미 정한 대로 **수동 검증 시나리오**로 따로 둔다.

### 3.2 채택하지 않은 것과 이유

| 후보 | 기각 사유 |
|---|---|
| **녹화 응답 (VCR)** | 녹화 시점에 **실제 토큰이 필요**해 S-4 위험을 만든다. 녹음본에 토큰·PII 가 섞이면 저장소에 그대로 커밋된다. 녹화본 드리프트의 갱신 주기도 정할 수 없고, LLM 은 비결정적이라 녹화의 의미가 애초에 약하다 |
| ~~WireMock~~ | **기각을 철회했다** — 위 §3.1 참조. 전송 계약 층은 WireMock 이 아니면 검증 수단이 없다 |

### 3.3 픽스처 위치·명명 규약 (FR-2)

세 종류를 각각 정한다.

#### ① 능력 대역 (페이크)

**자기가 구현하는 능력 인터페이스와 같은 패키지**에 둔다.

```
src/main/java/com/ossagent/issue/domain/IssueSource.java        ← 능력 (main)
src/test/java/com/ossagent/issue/domain/FakeIssueSource.java    ← 대역 (test · 같은 패키지)
```

중앙 집중(`com.ossagent.testing.fake`)을 쓰지 않는 이유 — 능력 인터페이스는 **도메인별로 흩어져**
있다(규율 ③). 대역만 한곳에 모으면 계약과 대역이 떨어져 한쪽만 고쳐지고, 패키지 경계를 넘느라
가시성을 전부 `public` 으로 열어야 한다. #35 가 이미 이 배치를 택했다.

이름은 **`Fake{능력이름}`**. **`Mock`·`Stub` 을 쓰지 않는다** — Mockito 의 mock 과 섞인다.

#### ② 값 픽스처

**자기가 만드는 타입과 같은 패키지**에 `{타입}Fixtures` 로 둔다. static factory 만, 상태 없음.

🔴 **애그리거트를 넘어 공유하지 않는다.** `candidate` 테스트가 `IssueFixtures` 를 쓰면
규율 ④ 가 막는 의존이 **테스트를 통해 되살아난다.** 남의 애그리거트 값이 필요하면
**자기 테스트 패키지에서 자기가 만든다.** 중복이 결합보다 싸다.

#### ③ 리소스 픽스처 (캔드 페이로드)

```
src/test/resources/github/{api}-{case}.json        HTTP 응답 본문 (MockRestServiceServer)
src/test/resources/policy/{case}/CONTRIBUTING.md   기여 규약 원문 (S-5 판정 입력)
src/test/resources/llm/{prompt}-{case}.txt         LLM 응답 원문 (깨진 출력 포함)
```

⚠ `src/test/resources/` 는 **아직 존재하지 않는다.** 첫 픽스처가 생길 때 만든다 —
빈 디렉토리는 git 이 추적하지 않는다. 이 PR 은 자리만 규약으로 정한다.

#### 공통 규율

🔴 **페이크는 `src/test` 에만 존재한다.** `src/main` 에 페이크·스텁·인메모리 구현을 두지 않는다.
운영 조립에서 실수로 선택될 수 있는 경로를 만들지 않기 위해서다.

🔴 **실패 모드를 재현할 수 있어야 한다** — 예외 · 빈 결과 · 깨진 LLM 출력 · 타임아웃.
「항상 성공만 반환하는 페이크」는 게이트를 검증하지 못한다. 이 제품의 품질 축은
「좋은 코드를 쓰는가」가 아니라 **「나쁜 결과를 걸러내는가」**다. S-6(재시도 상한 소진 → `FAILED`)
검증도 이 전제 위에 선다.

🔴 **픽스처에 실제 토큰을 넣지 않는다 (S-4).** 토큰 *형태*가 필요하면
**패턴에 매칭되지 않는, 가짜임이 눈에 보이는 고정 상수**를 쓴다.

```java
// ✅ ghp_[A-Za-z0-9]{36} 에 매칭되지 않는다(밑줄). 읽는 사람도 가짜임을 안다
static final String FAKE_TOKEN = "ghp_NOT_A_REAL_TOKEN_FOR_TESTS_ONLY";

// ❌ 런타임 조립 — secret-scan.sh 를 "피해 가는" 관용구다
static final String TOKEN = "ghp_" + "x".repeat(36);
```

⚠ 실제 토큰 **길이·문자셋**이 유의미한 테스트(마스킹 경계 검증 등)에서만 조립을 허용하고,
**왜 조립했는지를 그 줄의 주석에 남긴다.** 조립을 기본 관용구로 삼지 않는다.

### 3.4 `@SpringBootTest` 실어댑터 차단 (FR-3·FR-4)

**규칙** — 통합 테스트 컨텍스트에 `com.ossagent` 아래 **`github` · `llm` · `sandbox`** 패키지
세그먼트를 가진 빈이 올라와서는 안 된다. (`persistence` 는 **제외** — 실 DB 검증은 의도된 것이다.)

**장치 — 3개** (⚠ 초안은 2개였다. #35 머지로 실제 어댑터가 생기면서 배제 장치가 필요해졌다).

| # | 장치 | 무엇을 하는가 |
|---|---|---|
| 1 | `@AgentIntegrationTest` **합성 애노테이션** | 통합 테스트의 표준 진입점. `@SpringBootTest` + `@ActiveProfiles("test")` + 페이크 조립 |
| 2 | **`@Profile("!test")`** | 실제 대외 어댑터가 테스트 프로필에서 **스스로 빠진다** |
| 3 | **컨텍스트 가드** | 그래도 올라온 것이 있으면 **잡는다** |

**판정 규칙은 두 신호다** — 초안의 「패키지에 `github` 세그먼트가 있는가」는 `GitHubErrorTranslator`
(순수 변환)·`GitHubProperties`(설정값)까지 오탐했다.

| # | 신호 | 왜 |
|---|---|---|
| 1 | 패키지가 `adapter.out.{github·llm·sandbox}` **연속 3칸** | 규율 ③ 의 배치 규칙 |
| 2 | 필드로 **네트워크 클라이언트를 (전이적으로) 보유** | 이름이 아니라 **능력**으로 본다 |

신호 2 가 없으면 **패키지 이름을 바꾸는 것만으로 가드를 통과**할 수 있다 —
`support.github` → `support.client` 하나로 가드가 코드 변경 없이 영구 무력화된다.

**기각한 3번째 장치** — 「`@SpringBootTest` 직접 사용 금지」 정적 스캔.
이슈 요구 밖의 스타일 강제이고, 허용 목록 운영 비용이 새로 생긴다. 무엇보다
`ClassPathScanningCandidateComponentProvider` 는 기본적으로 **메타 애노테이션을 따라가므로**
`@AgentIntegrationTest` 를 쓴 **준수 클래스까지 전부 적발**한다(`considerMetaAnnotations=false` 필요).
필요해지면 별도 이슈로 다룬다.

⚠ **남는 구멍은 숨기지 않는다** — 테스트가 실어댑터를 `@Import` 로 직접 끼우면 장치 2가
자기 컨텍스트에서만 검사하므로 놓칠 수 있다. 현실적 누출 경로인 **`@Component` 스캔**은
장치 2가 잡는다(스캔 베이스가 `com.ossagent` 루트라 모든 컨텍스트가 같은 빈을 받는다).

⚠ **NFR-3 — 0건 검사로 통과하지 않게 한다.**
오늘 `main` 에는 대외 어댑터가 **하나도 없다**(#6 미머지). 장치 2 를 그냥 두면 **0개를 검사하고
초록**이 된다. **양성 대조**로 막는다 — 「판정기가 `adapter/out/persistence` 의 **실제 빈**을
찾아냈고 **허용**으로 판정했다」를 함께 단언한다. 검사 모수가 0 이 아님이 증명되고,
가짜 어댑터를 `@Component` 로 심어 **모든 컨텍스트를 오염시키는** 방식을 피한다.
판정 **규칙** 자체는 순수 함수라 유닛 테스트로 따로 증명한다.

이 방식은 `ExternalTextMarkerTest` 의 「규칙을 검사한다 + 검사 대상을 실제로 찾았다」 이중 구조와 같다.

### 3.5 테스트 스코프 S-3 정적 검사 (FR-6)

`safety-boundary-check.sh:80` 이 S-3 검사를 **`src/test` 에서 의도적으로 건너뛴다.**
그 결과 스프링을 쓰지 않는 평범한 JUnit 테스트가 `ProcessBuilder` 로 호스트에서 빌드를 돌리거나
`/var/run/docker.sock` 을 마운트해도 **아무 장치도 막지 않는다.** §3.1 의 샌드박스 결정
(「실제 컨테이너를 띄우지 않는다」)을 선언으로만 두지 않기 위해 **검사 범위를 테스트로 확대**한다.

기존 3개 테스트는 `ProcessBuilder`·docker.sock 을 쓰지 않으므로 **회귀가 없다.**
Testcontainers 는 Java API 를 쓰지 프로세스를 띄우지 않는다. 의도된 예외는 기존 관용구
`// safety-ok: <사유>` 로 처리한다.
