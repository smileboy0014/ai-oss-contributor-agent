# Improve Skill

## 역할

"무엇이 부족한가"를 발견했다면, "어떻게 고칠 것인가"를 설계하고 실행한다. 스킬과 훅의 **자기 개선 루프**.

## 사용법

```
/improve-skill                       # 최근 세션에서 개선점 탐색
/improve-skill <개선 대상 설명>        # 특정 개선 대상 지정
```

## 강제력 위계

개선 수단을 선택할 때 이 위계를 따른다:

```
훅 (기계적 차단, 100%) > 스킬 (워크플로우 강제, ~80%) > CLAUDE.md/Memory (참고, ~50%)
```

- **기계적으로 잡을 수 있는 규칙** → 훅으로 구현 (`.claude/scripts/` + `.claude/settings.json`)
- **워크플로우/판단이 필요한 규칙** → 스킬 SKILL.md 패치
- **맥락/배경 지식** → `.claude/rules/` 또는 memory (최후 수단)

> 🔴 **안전 경계(S-1~S-6)에 닿는 갭은 위계를 건너뛰지 않는다.**
> 정적으로 잡히면 반드시 훅까지 간다. "리뷰에서 보겠다"로 끝내지 않는다 —
> 이 프로젝트의 사고는 외부 OSS 커뮤니티로 나가고 되돌릴 수 없다.

## Step 0: 입력 확인

개선 대상을 파악한다. 소스는 다음 중 하나:

1. **사용자의 직접 피드백** — "이 스킬에서 이게 빠졌어", "이 워크플로우가 불편해"
2. **코드리뷰에서 반복된 지적** — 같은 유형의 이슈가 반복됨
3. **세션 중 발견** — 스킬이 놓친 케이스
4. **`/antipattern` 연계** — 안티패턴에서 훅화 불가능한 항목이 스킬 패치로 넘어옴

개선 대상을 표로 정리:

| 판정 | 대상 | 갭 설명 | 개선 방향 |
|------|------|---------|----------|
| 🔧 | /pr-review | 샌드박스 정리 누락 점검 없음 | 체크리스트에 운영 카테고리 추가 |
| ⚙️ | safety-boundary-check.sh | `Instant.now()` 차단 없음 | 정적 규칙 추가 |

🔧 = 스킬 패치, ⚙️ = 훅 추가/수정

## Step 1: 진단 — 스킬/훅 읽기

각 개선 대상에 대해:

1. **해당 파일을 읽는다**
   - 스킬: `.claude/skills/{name}/SKILL.md`
   - 훅 스크립트: `.claude/scripts/{name}.sh`
   - 훅 등록: `.claude/settings.json`
   - 룰: `.claude/rules/{context|conventions}/*.md`
2. **"이 갭을 방지하려면 어디에 뭘 추가/변경해야 하는가?"를 구체화한다**

진단 결과:

| 대상 | 현재 상태 | 부족한 점 | 패치 내용 |
|------|----------|----------|----------|
| pr-review SKILL.md | 운영 점검 없음 | 컨테이너 누수·토큰 미기록이 안 걸림 | 체크리스트에 「운영」 카테고리 추가 |

## Step 2: 훅화 가능성 판단

```
질문: "이 실수를 정적으로 감지할 수 있는가?"
  → Yes: 훅 구현 (⚙️) — .claude/scripts/ 스크립트 수정 또는 신규 + settings.json 등록
  → No: 스킬 패치 (🔧) — SKILL.md 또는 references/*.md 수정
```

### 어느 스크립트에 넣나

| 성격 | 스크립트 | 훅 이벤트 |
|---|---|---|
| 안전 경계 정적 위반 | [`safety-boundary-check.sh`](../../scripts/safety-boundary-check.sh) | `PreToolUse` — `Bash(git commit:*)` |
| 시크릿 패턴 | [`secret-scan.sh`](../../scripts/secret-scan.sh) | `PreToolUse` — `Bash(git commit:*)` |
| 빌드·정적검사 | [`pre-commit-check.sh`](../../scripts/pre-commit-check.sh) | `PreToolUse` — `Bash(git commit:*)` |
| 테스트 자동 실행 | [`impl-test-loop.sh`](../../scripts/impl-test-loop.sh) | `Stop` |
| 도구 실패 복구 안내 | `edit-recovery.sh` · `large-file-recovery.sh` · `tool-failure-tracker.sh` | `PostToolUseFailure` |
| 대용량 출력 축소 | `output-truncator.sh` | `PostToolUse` |

**기존 스크립트에 규칙을 추가하는 것이 우선**이다. 새 스크립트는 훅 이벤트가 다르거나 성격이 확연히 다를 때만 만든다.

### 훅 구현 시 체크리스트

- [ ] Pre or Post? — 차단이면 `PreToolUse`, 피드백이면 `PostToolUse`/`PostToolUseFailure`, 턴 종료 검증이면 `Stop`
- [ ] 대상 도구 matcher — `Bash(git commit:*)`, `Edit|Write` 등
- [ ] 제외 조건 — `src/test/**`, 주석 라인, `build/`, 스크립트 자기 자신
- [ ] 에러 메시지 — **조항 번호(S-?) + 무엇이 잘못이고 + 대안**
- [ ] 예외 경로 — `// safety-ok: <사유>` 를 존중하는가. 사유 없는 예외는 막는가
- [ ] **`bash -n` 문법 검사 통과**
- [ ] **오탐 테스트** — 정상 코드가 통과하는가
- [ ] `settings.json` 등록 + `chmod +x`
- [ ] **"검증을 실행하지 않았으면 통과라고 하지 않는다"** — 대상이 없어 스킵한 경우 그 사실을 출력한다

### 스킬 패치 시 체크리스트

- [ ] 어떤 Step/섹션에 추가하는가?
- [ ] 기존 흐름을 깨지 않는가?
- [ ] 추가된 내용이 모든 상황에 적용되는가, 특정 조건에만인가?
- [ ] 다른 스킬과 중복되지 않는가 (`/work`가 위임하는 스킬들끼리 규칙이 어긋나면 lifecycle이 갈라진다)

## Step 3: 실행

진단 결과에 따라 파일을 수정한다.

**수정할 때 반드시 보여줄 것:**
- **상황**: 어떤 갭이 발생했는가
- **원인**: 스킬/훅의 어느 부분이 부족했는가
- **패치**: 무엇을 어떻게 수정했는가
- **효과**: 다음 세션에서 어떻게 달라지는가

## Step 4: 검증

- **훅** → `bash -n` 문법 검사 + 위반 코드 차단 확인 + **정상 코드 통과 확인(오탐 없음)**
- **스킬** → 변경된 부분이 논리적으로 일관적인지 검토, 다른 스킬과 충돌 없는지 확인

훅 검증은 실제로 돌려본다. 시뮬레이션만으로 "될 것"이라고 보고하지 않는다.

## 결과 보고

```markdown
## /improve-skill 결과

### 패치 내역
- ⚙️ safety-boundary-check.sh — `Instant.now()` 직접 호출 차단 추가. 효과: 다음 커밋부터 `Clock` 미주입이 즉시 걸린다
- 🔧 pr-review SKILL.md — 운영 체크리스트(컨테이너 정리·토큰 기록) 추가. 효과: 리뷰에서 누수·비용 항목을 빠뜨리지 않는다

### 검증
- [x] 훅: bash -n 통과
- [x] 훅: 위반 코드 차단 확인
- [x] 훅: 정상 코드 통과 확인
- [x] 스킬: 논리 일관성 확인
```

## 종료 조건

- 모든 🔧/⚙️ 항목 패치 완료
- 검증 통과
- 결과 요약 제시

## `/antipattern` 연계

`/antipattern`에서 "맥락 판단 필요"로 분류된 항목이 스킬 패치로 넘어올 수 있다. 이 경우 해당 스킬의 체크리스트나 프로세스에 점검 항목을 추가한다.

반대로 `/antipattern`의 **훅 승격 후보** 목록에 있는 항목은 이 스킬에서 실제 승격을 수행한다.
