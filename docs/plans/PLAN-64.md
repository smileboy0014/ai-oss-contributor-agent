**이슈**: [#64](https://github.com/smileboy0014/ai-oss-contributor-agent/issues/64)

**작성일**: 2026-09-26
**작성자**: smileboy0014

## 1. 원인

`secret-scan.sh` 의 개인키 검사는 헤더가 **줄의 처음**(들여쓰기·목록 기호 제외)에 오는지를 본다.
UTF-8 BOM(`EF BB BF`)이 붙으면 그 3바이트가 **줄 시작을 차지**해 `-+` 에 닿지 않는다.

`.pem` 은 헤더가 **1행**이라 BOM 하나에 파일 전체가 샌다.

⚠️ **선재 구멍이다.** `#58` 이전의 `^-+` 도, 그 뒤의 `^[[:space:]]*-+` 도 같은 이유로 놓친다.

### 🔴 재현하려다 더 큰 것을 찾았다 — 로컬 `grep` 이 CI 와 다르다

프로브를 만들어 돌렸더니 **차단됐다.** 이슈에 적힌 것과 반대라 `grep` 자체를 확인했다.

```
$ grep --version
ugrep 7.8.4 aarch64-apple-macosx …
```

**이 개발 머신의 `grep` 은 `ugrep` 이다.** BSD 도 GNU 도 아니고, **BOM 을 알아서 건너뛴다.**

| 구현 | BOM 파일 판정 |
|---|---|
| `ugrep 7.8.4` (이 머신의 `grep`) | 🚫 차단 — **구멍이 안 보인다** |
| `/usr/bin/grep` (BSD 2.6, macOS 기본) | 🔴 **통과 — 샌다** |
| GNU grep 3.11 (CI·리눅스) | 🔴 통과 — 샌다 (`#58` 리뷰 실측) |

**로컬 게이트가 구멍을 가리고 있었다.** 커밋 훅은 `bash` 가 `PATH` 에서 찾은 `grep` 을 쓰므로,
이 머신에서 커밋할 때는 BOM 키가 차단되지만 **CI 와 다른 사람의 머신에서는 통과한다.**
반대 방향도 가능하다 — `ugrep` 이 더 넓게 잡으면 로컬에서만 빨개진다.

⚠️ 이것이 `#61`(브랜치별 초록이 합쳐진 뒤의 초록을 보장하지 않는다)과 **같은 계열**이다.
「내 환경에서 초록」이 「게이트가 작동한다」를 뜻하지 않는다.

## 2. 수정

### ① BOM 을 `read_file` 에서 벗긴다 — 정규식을 건드리지 않는다

`#58` 리뷰에서 내가 「ERE 에 `\xNN` 이 없어 스크립트에 리터럴 바이트를 박아야 한다」고
기각했는데 **그 전제가 정규식을 고친다는 가정에 묶여 있었다.**

`read_file()` 은 **모든 패턴이 통과하는 단일 지점**이다. 거기서 벗기면 정규식 7개를
전부 그대로 두고 한 곳만 고친다.

⚠️ 첫 줄에만 적용한다. 파일 중간의 `EF BB BF` 는 BOM 이 아니라 **정상 문자**(U+FEFF)다.

### ② 🔴 `grep` 구현을 고정한다 — 이번 건의 진짜 교훈

BOM 만 고치면 **다음 함정이 같은 자리에서 또 난다.** 게이트가 어떤 `grep` 으로 도는지
모르는 채로는 「로컬에서 확인했다」가 아무것도 보장하지 않는다.

**할 수 있는 것과 없는 것을 가른다.**

| 안 | 판정 |
|---|---|
| 특정 구현을 요구한다 (GNU 필수 등) | ❌ macOS 기본에 GNU grep 이 없다. 개발 환경을 강제할 수 없다 |
| **스크립트가 쓰는 `grep` 을 기록한다** | ✅ **채택** — 게이트 출력에 남겨 「어느 구현으로 통과한 초록인가」를 보이게 한다 |
| 동작 차이를 자가 진단한다 | ✅ **채택** — BOM 처리 여부를 기동 시 한 번 확인하고 다르면 경고 |

②는 **구멍을 닫지 않는다.** 구멍이 **보이게** 만든다 — 그게 이번에 없던 것이다.

## 3. 검증

| # | 검증 | 방법 |
|---|---|---|
| 1 | 🔴 **BOM 붙은 키가 차단된다** | `/usr/bin/grep`(BSD)로 확인 — `ugrep` 은 구멍을 가린다 |
| 2 | BOM 없는 키는 계속 차단 (회귀) | 〃 |
| 3 | 🔴 **`read_file` 변경이 다른 패턴을 깨뜨리지 않는다** | 전 패턴 공용 함수다. 토큰 5종 · JSON · `.env` 검사 · 바이너리 스킵 |
| 4 | `SCAN_MODE=tree`·`staged` **양쪽** | 두 경로가 `read_file` 구현이 다르다(`cat` vs `git show`) |
| 5 | 추적 파일 전체 **히트 0건** | 넓히기 전 필수 절차 |
| 6 | **드리프트 테스트 샘플에 BOM** | 없으면 이 구멍에 양성 대조가 없다 |
| 7 | 물림 | BOM 스트립을 빼면 6이 빨개진다 |
| 8 | 🔴 **`ugrep`·BSD grep 양쪽에서 1~5** | 이번 건이 그 차이에서 나왔다 |

### 6번이 핵심이다

`#58` 에서 드리프트 샘플을 들여쓴 형태로 바꿔 그 구멍에 양성 대조를 세웠다. **BOM 은 아직
없다.** 넣지 않으면 이 수정이 나중에 되돌려져도 초록이다.

⚠️ 다만 **Java 쪽 샘플에 BOM 을 넣는 것으로는 부족하다.** 드리프트 테스트는 스크립트
정규식을 **Java 로 컴파일해** 샘플을 대조하는데, Java 는 BOM 을 특별 취급하지 않는다.
스크립트의 BOM 처리는 **`read_file` 에 있지 정규식에 없으므로** 그 테스트가 볼 수 없다.
→ **셸 쪽 검증이 필요하다.** §5 에서 판단한다.

### §3-6 의 보류를 결론으로 — 셸 검증 수단이 있었다

「드리프트 테스트로는 볼 수 없다」까지는 맞았다. 그 테스트는 정규식만 뽑아 Java 로
컴파일하는데 BOM 처리는 `read_file` 의 파이프에 있다.

**그래서 스크립트를 실제로 돌리는 테스트를 만들었다.** `testing-philosophy.md` 가
「우리 저장소의 `.claude/scripts/*.sh` 를 테스트에서 돌리는 것은 S-3 대상이 아니므로
`// safety-ok` 로 예외 처리한다」고 이미 길을 터 놨다 — 없던 수단이 아니라 **내가 안 본
수단**이었다.

🔴 **그리고 이것이 BOM 보다 큰 것을 잡는다.** 그 환경의 `grep`·`sed`·`bash` 로 실제
실행하므로 **「내 머신에서 초록」이 아니라 「이 실행 환경에서 초록」**을 증명한다.
CI 가 다른 `grep` 을 쓰면 **CI 에서 빨개진다** — 이번 건에 없던 신호가 정확히 그것이다.

임시 git 저장소를 만들어 돌리므로 실제 저장소를 건드리지 않는다.
⚠️ 스크립트는 저장소 밖에서 조용히 `exit 0` 이 되므로, **「실제로 실행했다」를 단언하는
검사**를 함께 뒀다 — 안 돌고 초록인 것이 이 테스트의 고유한 함정이다.

#### 🔴 그 테스트를 커밋하려다 게이트에 막혔다 — 그리고 그게 맞다

픽스처를 Java 텍스트 블록으로 썼더니 헤더가 **줄 시작**에 왔고, 그게 바로 이 게이트가
잡는 모양이라 **커밋이 차단됐다.**

`secret-scan.sh` 주석이 그 경우를 예고하며 적어 둔 대로 했다 —
**「화이트리스트를 되살리는 것은 답이 아니다. 예시 쪽을 고쳐라」**(#58).
`String.join` 으로 바꾸니 소스의 각 줄이 `"` 로 시작해 걸리지 않는다.

⚠️ `#58` 에서 내가 **정확히 반대로** 했던 자리다. 그때는 문서 한 줄을 통과시키려고
화이트리스트를 넣었고, 그것이 **진짜 키 파일을 통과시키는 회귀**가 되어 리뷰에서 잡혔다.
같은 상황에서 같은 유혹이 왔고, 이번엔 주석이 먼저 말려 줬다 —
**한계를 적어 두는 것이 다음번의 나를 막는다.**
