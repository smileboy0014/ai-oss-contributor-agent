## 0. 계약 표면

```
issue/domain                                  ← 순수 판정 (기술 없음 · 대외 호출 0)
  IssueFilter     .evaluate(Issue) → FilterVerdict
  FilterRule      규칙 하나 = 클래스 하나
  FilterOutcome   PASSED · REJECTED · UNDECIDED
  LabelPriority   순수 함수 — 점수 계산
        ▲
issue/application
  FilterIssuesUseCase   페이지 단위 판정 적재 (트랜잭션 경계)
```

**대외 호출이 없다.** 이 단계의 존재 이유가 「LLM 에 넣기 전에 **싸게** 거른다」이므로,
여기서 GitHub 을 더 부르면 목적이 무너진다. 입력은 **이미 저장된 `Issue` 행**뿐이다.

### 스키마 — **V7** (「변경 없음」을 철회했다)

계산해 놓고 버리는 값이 둘 있어 컬럼을 추가한다.

```sql
ALTER TABLE issue ADD COLUMN comment_count    INTEGER;
ALTER TABLE issue ADD COLUMN filter_priority  SMALLINT;
ALTER TABLE issue ADD COLUMN filter_judged_at TIMESTAMP(6) WITH TIME ZONE;
ALTER TABLE issue ALTER COLUMN filter_reason SET DATA TYPE VARCHAR(512);
```

| 컬럼 | 왜 필요한가 |
|---|---|
| `comment_count` | **rev.3 에서 추가.** #8 이 「이슈 #9 를 위해」 수집해 놓고 영속하지 않았다 — 규칙 ③ 이 입력으로 쓸 수 없는 상태였다. 컬럼이 없으면 `HEAVY_DISCUSSION` 이 선언만 되고 발화하지 않는다 |
| `filter_priority` | FR-4 의 산출물. `FilterVerdict` 는 **반환값**이라 트랜잭션이 끝나면 사라진다. #11 이 분석 순서를 정할 때 **SQL 정렬**로 써야 하는데 Java 함수로는 못 한다 |
| `filter_judged_at` | 「판정이 언제 섰나」. `updated_at`(행을 언제 건드렸나)과 뜻이 다르다 |
| `filter_reason` 타입 | 값이 enum 이름으로 제약되어 **외부 텍스트가 아니게 됐다** — 아래 S-4 절 |

### ⚠️ rev.2 정정 — `filter_judged_at` 은 경합을 자가치유하지 못한다

rev.2 는 `updatedAt > filterJudgedAt` 로 경합을 푼다고 적었다. **틀렸다.**

경합은 이렇게 난다 — 필터가 본문 A 를 읽는 사이 스캔이 B 로 갱신하며 `filterResult` 를
비우고, 그 뒤 필터가 A 기준 판정을 쓴다. 이때 `filterJudgedAt` 은 **벽시계라 스캔의
`updatedAt` 보다 늦다.** 조건이 성립하지 않아 그 행은 「최신 판정」으로 보인다.

내용 버전(`github_updated_at`)을 저장하면 풀리지만, **지금 그 경합은 존재하지 않는다** —
스케줄러가 없어 동시 실행 경로 자체가 없고, `IssuePageWriter` 가 스캔-스캔 경합을 이미
같은 자리(#14)에 남겨 뒀다. **실재하지 않는 경합을 위해 컬럼 의미를 비틀지 않는다.**

> **결정** — 경합은 스캔과 필터를 **저장소별로 직렬화**해 막는다. 그 책임은 스케줄러를
> 붙이는 **#14** 다. `filter_judged_at` 은 「규칙을 바꾼 뒤 낡은 판정을 골라낸다」는
> 운영 용도로만 남긴다.

⚠️ 벤더 고유 문법 금지(Q-2). H2·PostgreSQL 공통 문법만 쓴다.
⚠️ V7 은 **선점 통지 완료** — #13·#28 세션 모두 마이그레이션 없음.

### 🔴 S-4 — `filterReason` 에 자유 텍스트를 넣지 않는다

`filter_reason` 은 String 열이다. 구조로 막지 않으면 이슈 본문 발췌가 들어간다.

**`FilterReason` enum 의 `name()` 만 쓴다.** (rev.3 개명 — `SHORT_BODY` 처럼 **배제가 아닌**
사유가 있어 `RejectionReason` 은 거짓말이 된다.) 자유 문자열을 받는 경로를 만들지 않는다 —
사유는 「왜 떨어졌나」의 **코드**이지 증거 인용이 아니다.

그래서 `Issue.filterReason` 의 `@ExternalText(TARGET_REPOSITORY)` 를 **떼고 컬럼도
`TEXT` → `VARCHAR(512)` 로 내렸다.** 값이 더 이상 대상 저장소 텍스트가 아니라 **우리 어휘**다 —
`RepositoryPolicy.pendingReason`(V5)과 같은 판단이다.

⚠️ rev.2 는 「컬럼 타입은 그대로 둔다」고 적었으나 **선택지가 없었다.** `ExternalTextMarkerTest`
가 「`TEXT` 로 매핑된 `String` 필드는 예외 없이 `@ExternalText` 를 갖는다」를 빌드에서 강제한다.
마커만 떼면 빌드가 깨진다 — 규칙이 실제로 작동한 것이다.

S-4 는 프롬프트만의 문제가 아니다. **대상 저장소 텍스트가 우리 DB 를 거쳐 나중에
LLM·PR 본문으로 흘러가는 경로**가 같은 문제다 — #7 의 `contribution_rules` 가 그랬다.

※ #28 이 `IssueSnapshot` compact 생성자에 스크럽을 넣으므로 `issue.body` 는 전이적으로 닫힌다.
`@ExternalText` 등록표의 `filterReason` 행은 이 PR 이 갱신한다.

## 3. 기술 설계

### 규칙 4개 — **②는 규칙이 아니다**

| # | 규칙 | 이 PR 에서 |
|---|---|---|
| ① | 이미 종료됨 | ✅ 구현. ⚠️ 데이터 부재로 **현재 미발화** |
| ② | 활성 PR 존재 | 🔴 **규칙 클래스로 만들지 않는다** — 아래 |
| ③ | 요구 불명확 | ✅ 구현 (확정분 + LLM 인계분으로 가름) |
| ④ | 대규모 변경 | ✅ 구현 (라벨만) |

#### 🔴 ② 를 규칙에서 뺀 이유 — 규칙이면 `PASSED` 가 죽는다

「항상 `UNDECIDED` 를 내는 규칙」을 두면, 집계에서 **배제되지 않은 100% 가 `UNDECIDED`** 가 되고
**`PASSED` 는 도달 불가능한 죽은 값**이 된다. 그러면 하류 #11 은 `UNDECIDED` 를 통과로 취급할
수밖에 없고 — **「판정하지 않았다」를 「통과」로 뭉개는 것을 막겠다는 명분이 한 층 위에서
그대로 재현**된다.

**입력과 무관하게 같은 값을 내는 것은 규칙이 아니라 구멍이다.** 이슈 단위 판정이 아니라
**단계 전체의 공백**이므로, 행마다 기록하지 않고 ①의 공백과 같은 자리에 문서로 남긴다.

**왜 미루는가** — 알아내려면 Search API(**30 req/min**, `external-deps.md` 가 「스캐너가 가장 먼저
부딪힌다」고 경고한 한도) 또는 **이슈당 Timeline 1호출**이다. 수천 건 전량에 대해 그 비용을 치르면
아끼려던 것보다 더 쓴다.

⚠️ **미루는 지점은 #22 가 아니다.** #9 의 목적은 「**분석 비용**이 늘어나는 것을 막는다」인데
#22 는 LLM 분석·계획·코딩·샌드박스(최대 30분)·AI 리뷰를 **전부 태운 뒤**다. 이슈당 HTTP 1회를
아끼려고 후보당 파이프라인 1회를 지불하는 셈이라 **비용 방향이 역전**된다.

후보가 처음으로 극소수가 되는 지점은 **필터를 통과해 LLM 분석에 들어가기 직전(#11 입구)** 이다.

> **#11 입구에서 1회 + #22 에서 재확인 1회.** 재확인이 필요하다는 것은 「#22 에도 둔다」는
> 뜻이지 「#11 에 두지 않는다」는 뜻이 아니다.

#### ③ 요구 불명확 — 확정분과 LLM 인계분을 가른다 (FR-3 의 핵심)

| 신호 | 판정 | 왜 |
|---|---|---|
| 본문이 `null`·공백뿐 | **`REJECTED`** | 판정할 것이 없다. 확정이다 |
| 본문이 상한 미만 | **`UNDECIDED`** | 짧다고 불명확한 것이 아니다 — 스택트레이스 링크 한 줄짜리 명확한 버그 리포트가 있다 |
| 코멘트가 많다 | **`UNDECIDED`** | 상관은 있어도 인과가 아니다 — 활발한 논의일 수도 있다 |

⚠️ **본문 길이와 코멘트 수에 같은 잣대를 댄다.** 처음엔 코멘트 수만 「상관일 뿐」이라며 버렸는데,
**본문 길이도 똑같이 상관일 뿐**이다. 장문의 모호한 기능 요청이 있고 짧고 명확한 버그 리포트가 있다.
둘 다 **배제가 아니라 LLM 인계**로 보내는 것이 완료조건 3(「규칙 가능분과 LLM 필요분 구분」)의
충실한 이행이다.

`min-body-length` **기본 200자** — 공백 제거 후 기준. 근거: GitHub 이슈 URL 하나가 60~80자라
「링크만 붙인 이슈」를 잡으려면 그보다 커야 하고, 한두 문장짜리 정상 버그 리포트(100~150자)를
확정 배제하지 않으려면 그 위여야 한다. **확정 배제가 아니라 `UNDECIDED`** 라 경계가 다소
어긋나도 손실이 크지 않다. Phase 1 대상에서 실측 후 조정한다.

#### ④ 대규모 변경 — 라벨만

| 신호 | 판정 |
|---|---|
| `breaking-change`·`breaking` 라벨 | `REJECTED` |
| `epic`·`rfc`·`design` 라벨 | `REJECTED` |
| **본문 키워드** | 🔴 **쓰지 않는다** — 「refactor」가 본문에 있다고 대규모가 아니다. 오탐이 크다 |

라벨은 **메인테이너가 붙인 명시적 신호**라 신뢰도가 다르다.

### 🔴 집계 규칙 — 이것을 정의하지 않으면 위가 전부 무의미하다

```
REJECTED 가 하나라도 있으면        → REJECTED
아니고 UNDECIDED 가 있으면         → UNDECIDED
전부 통과면                        → PASSED        ← 도달 가능해야 한다
```

**모든 규칙을 평가하고 매치된 사유를 전부 수집**한다. 첫 매치에서 끊으면(short-circuit)
사유 분포가 **규칙 순서의 함수**가 되어, FR-2 가 노린 「분포를 보고 규칙을 고친다」가 불가능해진다.

`filter_reason` 에는 **걸린 사유를 전부** 콤마로 이어 저장한다 (rev.3 정정).

⚠️ rev.2 는 「대표 사유 1개 + 선정 우선순위 문서화」로 갔는데, 그러면 **저장된 분포가
여전히 편향된다** — 문서화된 편향도 편향이다. 사유 코드 6종을 전부 이어도 100자 남짓이라
전량 저장의 비용이 없다. 순서는 `FilterReason` **선언 순서**로 정규화한다 — 같은 입력이
같은 문자열로 저장돼야 집계가 된다.

**저장 어휘는 4상태다** — `NULL`(미판정) · `PASSED` · `REJECTED` · `UNDECIDED`.

### 라벨 우선순위 (FR-4)

`good first issue` · `help wanted` · `bug` · `enhancement` · `documentation` 순으로 점수.

⚠️ **없다고 배제하지 않는다.** 대부분의 이슈에 이 라벨이 없다 — 배제하면 Phase 1 대상
(`spring-kafka` 단일)이 거의 다 떨어진다. 이슈 문구도 「우선 **탐색** 라벨」이다.

점수는 `filter_priority` 에 **영속**한다 — 안 그러면 계산하고 버린다.

### 라벨 매칭 규칙 — 정의해야 테스트가 쓸 수 있다

`Issue.labels` 는 **콤마 조인 String** 이라 `IssueSnapshot` 의 `List<String>` 보다 정보가 열화돼 있다.
라벨은 ④의 **유일한 신호**이자 FR-4 의 입력이므로 여기가 약하면 둘이 같이 약해진다.

`Issue` 에 접근자를 추가한다 — `labelList()` · `hasLabel(String)` (`IssueSnapshot` 과 같은 semantics).

| 변이 | 매칭 |
|---|---|
| 대소문자 | 무시 |
| `breaking change` vs `breaking-change` | 구분자(`-`·`_`·공백) 동일 취급 |
| `type: enhancement` | `:` 뒤를 접미로 인정 |

### `FilterIssuesUseCase` — 페이지 단위

`Issue.body` 는 TEXT 이고 저장소 하나에 이슈가 수천 건이다. 전량을 한 트랜잭션에 적재하면
메모리·커넥션 점유가 커진다. **페이지 200건 · 페이지마다 트랜잭션.**

조회 조건 — `filterResult IS NULL OR updatedAt > filterJudgedAt` (미판정 + 낡은 판정).

⚠️ **설정값(`min-body-length` 등)을 바꿔도 기존 판정은 재판정되지 않는다.** `filter_judged_at` 은
**내용 변경**만 잡는다. 기준을 조정하면 운영 절차로 `UPDATE issue SET filter_result = NULL` 이
필요하다 — 이 사실을 문서에 남긴다. 자동화(규칙 버전 해시)는 설정이 실제로 자주 바뀌면 그때.
