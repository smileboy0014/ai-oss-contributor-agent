조사해 보니 **골격은 이미 서 있다.** #6 이 `TokenRedactor` 를, #10 이 `PromptScrubber`

못하게 장치를 세우는 것**이다.

### 🔴 실재하는 구멍 ① — 패턴 목록이 이미 어긋나 있다

이슈가 「두 곳이 어긋나면 한쪽만 막힌다」고 경고한 그 일이 **이미 일어나 있다.**

| 패턴 | `secret-scan.sh` | `TokenRedactor` |
|---|---|---|
| `AKIA…` · `github_pat_…` · `xox…` · `sk-ant-…` | ✅ | ✅ |
| GitHub 토큰 | `ghp_`·`gho_` 각각 `{36}` | `gh[pousr]_` `{20,}` |
| **PEM 개인키 블록** | ✅ `^-+BEGIN [A-Z ]*PRIVATE KEY-+` (`:117`) | ❌ **없다** |

**커밋은 막히는데 런타임에는 모델로 나간다.** 대상 저장소가 개인키를 커밋해 뒀고 우리가
그 파일을 읽어 프롬프트에 넣으면, 스크럽을 통과해 **그대로 전송된다.**

⚠️ 어긋남은 **양방향**이다. 런타임에만 있는 `ghu_`·`ghs_`·`ghr_` 와 `{20,}` 폭은
스크립트에 없어, **우리 저장소에 그 형태의 토큰을 커밋해도 pre-commit 이 통과시킨다.**
「같은 목록을 공유」(완료 조건 7)는 한 방향이 아니다.

팩토리가 스크럽을 강제**하는 구조인데, `issue.body` 만 그 패턴 밖에 있다.

#### 🔴 NFR-3 정정 — 「선형」은 측정하지 않고 쓴 말이었다 (2026-09-26)

초안은 성능을 「선형이면 충분」으로 적고 넘어갔다. **선형인지 확인한 적이 없다.**
safety-reviewer 가 실측하자 **2차식**이었다.

| 입력 길이 | 소요 |
|---|---|
| 8.2 KB | 294 ms |
| 32.8 KB | **4,407 ms** |
| 131.2 KB | **76,006 ms** |

원인 — `BEGIN…[\s\S]*?…END` 는 **`END` 없는 `BEGIN` 마다 입력 끝까지 재스캔**한다.
평문·정상 diff 는 전부 선형이었고, **이 한 모양에서만** 무너졌다.

**실전 영향이 작지 않다.** GitHub 이슈 본문 상한이 65,536자이고, 스크럽은
`IssueSnapshot` 을 통해 **수집되는 모든 이슈**가 지나는 자리다. 길이 상한도 타임아웃도 없다.

정규식을 더 정교하게 만드는 대신 **줄 단위 스캐너**로 바꿨다 — 보안 핵심부를 읽어서
검증할 수 있게 하려는 것이었다.

#### 🔴 그런데 그 수정도 「선형」이 아니었다 (2차 리뷰)

「각 문자를 한 번만 보므로 선형이 구조적으로 보장된다」고 적었는데 **또 틀렸다.**
스캐너로 바꿔도 **헤더·푸터 정규식 선두의 `-+` 자체가 2차식**이고, 그것을 입력 전체와
블록 안의 줄마다 돌린다. 대시만 이어진 입력(마크다운 구분선)에서 재현된다.

| 대시 수 | 소요 |
|---|---|
| 8,000 | 157 ms |
| 64,000 | 11,003 ms |
| 200,000 | **197,709 ms (3분 18초)** |

그리고 그 입력은 **비용을 다 치르고 아무것도 가리지 못했다** — 느리고 안 막혔다.

⚠️ **내가 만든 회귀 테스트가 이것을 못 쟀다.** 고쳐진 입력 모양(`BEGIN` 헤더 반복) 하나만
재고 있었고, 대시가 5자뿐이라 두 경로 어느 쪽도 건드리지 못했다.
**「회귀 테스트를 넣었다」가 「그 회귀를 잰다」를 뜻하지 않는다.**

`-{1,10}` 으로 상한을 둬 닫았다. 탐지력은 줄지 않는다 — 스캔이 시작 위치를 옮겨 가므로
대시가 20개든 헤더 직전 10개가 잡힌다. 회귀 테스트에 **대시 런 2종**을 추가했다.

⚠️ 남길 교훈 두 개 —
1. **성능 서술은 측정하지 않으면 적지 않는다.** 「충분하다」는 판단이 아니라 추측이었다
2. **「구조적으로 보장된다」는 말은 그 구조를 전부 세어 본 뒤에만 쓴다.** 스캐너 본체는
   선형이었지만 그것이 부르는 정규식은 아니었고, 나는 본체만 보고 그 말을 썼다

## 3. 설계

### 3.1 🔴 드리프트를 **테스트로** 잡는다 (FR-7 · FR-3)

셸 스크립트와 Java 가 리터럴을 공유할 방법은 없다. 세 가지를 검토했다.

| 안 | 판정 |
|---|---|
| 공통 패턴 파일(`secret-patterns.txt`)을 **양쪽이 읽는다** | ❌ 스크립트는 `.claude/`(개발 하네스)에 있고 배포물이 아니다. 런타임이 그 파일에 의존하면 **파일이 없는 환경에서 스크럽이 조용히 0 이 된다** — 최악의 실패 모드 |
| Java 가 정본이고 스크립트를 **생성**한다 | ❌ 생성물을 커밋해야 하고, 누가 손으로 고치면 다음 생성에서 조용히 덮인다 |
| **드리프트 검출 테스트** | ✅ **채택** |

「공유」의 목적은 같은 파일을 쓰는 것이 아니라 **어긋나지 않는 것**이다.

#### (a) 추출기는 스크립트의 **두 표기 형태를 모두** 먹어야 한다

`secret-scan.sh` 의 패턴 표기가 균일하지 않다.

| 형태 | 위치 | 예 |
|---|---|---|
| `scan_pattern` 인자 (줄 이어짐 `\` 포함) | `:92-114` — 6개 | `'AKIA[0-9A-Z]{16}' "$f"` |
| **인라인 `grep -nE`** | **`:117` — PEM 단 하나** | `grep -nE '^-+BEGIN [A-Z ]*PRIVATE KEY-+'` |

⚠️ **`scan_pattern` 만 훑는 추출기는 하필 PEM 만 놓친다.** 이 PR 이 닫으려는 바로 그
패턴이 검출기 사각지대가 된다. 그래서 추출기는 줄 이어짐을 먼저 접고, `scan_pattern`
과 `grep -nE` 양쪽에서 작은따옴표 리터럴을 집는다.

#### (b) 「0건 방지」를 **개수**가 아니라 **집합 일치**로 한다

`count > 0` 은 PEM 을 놓친 채 6개를 세고 초록이 된다. 대신 추출 결과가
**기대 집합과 정확히 같은지** 단언한다. 스크립트에 패턴을 더하거나 빼거나 고치면
그 순간 빨개지고, PEM 이 빠지는 일은 **구조적으로 불가능**해진다.

#### (c) 비교는 리터럴이 아니라 **샘플 재현**으로 한다

리터럴 비교는 성립하지 않는다 — `ghp_[A-Za-z0-9]{36}` 과 `gh[pousr]_[A-Za-z0-9]{20,}` 은
문자열로 다르지만 **런타임이 더 넓다.** 그렇다고 임의 정규식에서 샘플을 자동 생성하는 것은
이 PR 의 분량이 아니고, 무엇보다 **PEM 에서 깨진다** — 스크립트 패턴은 헤더 한 줄이고
런타임 패턴은 블록 전체라((d) 참조) 자동 생성 샘플이 거짓 드리프트를 만든다.

**대응표를 테스트에 둔다.** 추출된 스크립트 패턴마다 행이 하나씩 있고, 각 행은
「이 시크릿 모양의 샘플을 `TokenRedactor.redact` 에 넣으면 원문 조각이 사라진다」를
**실제로 실행해** 증명한다. 행이 없는 패턴이 추출되면 실패한다.

| 얻는 것 | 잃는 것 |
|---|---|
| 커버리지가 **실행으로** 증명된다 (선언이 아니다) | 패턴을 추가할 때 행을 하나 써야 한다 |
| PEM 처럼 표현이 다른 경우를 정직하게 다룬다 | — |

⚠️ **샘플은 런타임 조립이지만, 그것이 기본값이어서가 아니다.**
`testing-philosophy.md` 는 런타임 조립을 **「검사를 피하는 것」으로 보고 금지**하며
가짜임이 보이는 고정 상수(`"ghp_NOT_A_REAL_TOKEN_FOR_TESTS_ONLY"`)를 기본으로 둔다.
예외는 **「토큰의 길이·문자셋이 실제로 유의미한 테스트(마스킹 경계 등)」** 인데,
이 대응표가 정확히 그 경우다 — 패턴에 **매칭되어야** 마스킹을 증명할 수 있고,
권장 상수는 밑줄 때문에 `[A-Za-z0-9]{20,}` 에 **매칭되지 않는다.**
규약대로 **그 줄에 조립 사유를 주석으로 남긴다.**

⚠️ `github_pat_` 은 `[A-Za-z0-9_]{20,}` 라 **밑줄을 허용**한다. 같은 관용구로 고정 상수를
만들면 스캐너에 걸린다 — 접두어마다 다르다.

#### (d) 🔴 PEM 패턴을 **헤더 앵커로 복사하면 유출을 막지 못한다**

스크립트 패턴 `^-+BEGIN [A-Z ]*PRIVATE KEY-+` 를 그대로 Java 로 옮기면 두 가지가 깨진다.

| 문제 | 결과 |
|---|---|
| `Pattern.MULTILINE` 없이 `^` 는 **입력 전체의 시작**이다 | 파일 내용 한가운데 낀 PEM 블록이 **아예 안 잡힌다** — 프롬프트에 파일을 넣는 현실 케이스가 정확히 그것이다 |
| 헤더 한 줄만 매칭된다 | 잡혀도 **헤더만 가려지고 키 본문은 그대로 나간다** |

**런타임은 `BEGIN` 부터 `END` 까지 블록 전체를 `DOTALL`·`MULTILINE` 으로 먹는다.**
테스트 케이스도 「텍스트 중간에 낀 PEM 블록」으로 잡는다 — 헤더만 있는 샘플로 테스트하면
초록인데 새어 나간다.

#### (e) 역방향은 **스크립트를 런타임 쪽으로 올려** 닫는다

런타임에만 있는 `ghu_`·`ghs_`·`ghr_` 와 `{20,}` 폭이 스크립트에 없다. 허용리스트로
기록만 하고 넘길 수도 있지만, **이건 실손해가 있는 구멍**이다(그 형태 토큰을 커밋해도
pre-commit 이 통과시킨다). 스크립트의 `ghp_{36}` · `gho_{36}` 두 항목을
**`gh[pousr]_[A-Za-z0-9]{20,}` 하나로 합쳐 런타임과 같게 만든다.**

합치고 나면 런타임 전용으로 남는 것은 `AUTHORIZATION_VALUE` 하나다. 이것은
`Authorization: Bearer …` 가 문서·테스트에 정상적으로 등장해 커밋 차단으로 쓸 수 없다 —
**런타임 전용 목록에 사유와 함께 명시**하고, 그 목록도 테스트가 고정한다.

### 3.2 파일 배제는 **최소 시그니처로** 두고, 계약은 #15 가 확정한다 (FR-2)

지금 대상 저장소 파일을 프롬프트에 넣는 경로는 **없다.** #7 은 고정 경로 목록
(`CONTRIBUTING.md` 등)만 읽어 배제가 필요 없고, 키워드 코드 검색은 **#15** 다.

그래도 **지금 만든다** — 이슈가 명시한 완료 조건이고(FR-2), 소비자가 없어도 목록의
정확성은 테스트로 고정되며, #15 가 급할 때 「배제 목록을 어디 두지」부터 고민하면 그때 빠진다.

⚠️ **소비자가 없으므로 시그니처가 추측이다.** 경로가 repo-relative 인지 절대경로인지,
`secrets/` 가 최상위만인지 임의 깊이인지, `.ENV`·`.env.production.local` 을 어떻게 볼지가
전부 미정이다. 그래서 **`boolean isSecretPath(String repoRelativePath)` 단일 메서드로
최소화**하고, javadoc 에 「#15 가 계약을 확정한다」를 적는다. 지금 정책 객체·설정 주입으로
키우면 **진짜 스코프 크립**이 된다.

### 3.3 🔴 「앞으로 빠질 수 없게」를 **할 수 있는 방법으로** 만든다 (FR-6 · FR-4)

가장 중요한 요구다. 그리고 가장 과장하기 쉬운 자리다.

#### 할 수 없는 것을 먼저 적는다

**「이 대입이 스크럽을 거쳤는가」는 데이터 흐름 분석이고, 리플렉션으로는 알 수 없다.**
`@ExternalText` 필드를 훑어 「스크럽했는가」를 판정하는 검사는 **만들 수 없다.**
할 수 없는 것을 할 수 있는 척하는 것이 #4·#43 에서 반복해 나온 실패다.

#### 대신 이 저장소가 이미 두 번 쓴 패턴 — **강제 지점**

막혀 있는 세 곳은 전부 같은 모양이다.

| 필드 | 강제 장치 |
|---|---|
| `agent_run.error_message` | `AgentRun.fail(...)` 이 유일한 대입 지점이고 거기서 `redact` |
| `repository_policy.contribution_rules` | `ScrubbedRules` 값 타입을 거치지 않으면 대입이 불가능 |
| LLM 프롬프트 | 어댑터 생성자가 `scrubber == null` 을 거부 |

**`issue.body` 에도 같은 것을 만든다.** `IssueSnapshot` 의 compact 생성자는 이미
`body = body == null ? "" : body` 로 **모든 이슈 본문이 통과하는 정규화 지점**이다.
여기서 `redact` 하면 — DB 로 가든 프롬프트로 가든 — 스크럽되지 않은 본문이
**존재할 수 없게** 된다. 한 줄이다.

`title` 도 같이 처리한다. 마커가 없는 이유는 `TEXT` 가 아니라서일 뿐이고
(`ExternalTextMarkerTest` 의 규칙이 `TEXT` 컬럼이다), **컬럼 길이는 보안 경계가 아니다.**
`labels` 는 제외한다 — 라벨 이름은 메인테이너가 정한 짧은 식별자이지 자유 텍스트가 아니다.

⚠️ 이것으로 `issue.filter_reason`(#9)도 **전이적으로** 닫힌다 — 이미 스크럽된 본문을
인용하기 때문이다. 다만 #9 이 다른 원문을 끌어올 수 있으므로 아래 등록표에 계약으로 남긴다.

#### 남은 필드는 **등록표**로 — 자동 판정이 아니라 리뷰 강제

리플렉션으로 `@ExternalText` 필드를 **열거**하고, 각각이 테스트의 표에 한 행씩 있기를
요구한다. 행에는 스크럽 수단을 적는다.

| 값 | 뜻 |
|---|---|
| `강제 지점` | 대입 경로가 하나이고 거기서 스크럽한다 |
| `값 타입` | 스크럽된 값 타입 없이는 대입이 불가능하다 |
| `미구현 — #N` | **쓰는 코드가 아직 없다. #N 이 위 둘 중 하나를 세워야 한다** |

마커를 단 새 필드가 표에 없으면 **빌드가 깨진다.** 이것이 강제하는 것은
「스크럽했다」가 아니라 **「스크럽을 어떻게 할지 누군가 정했다」** 이다 — 그 차이를
테스트 javadoc 과 PR 본문에 그대로 적는다.

이 표가 `contribution_candidate.analysis`(#13) · `issue.filter_reason`(#9) ·
`generated_change.*`(#18·#19)에 대한 **이 PR 의 산출물**이다. 계약을 남기지 않으면
그 이슈들이 원시 `String` 에 그대로 대입한다.

### 3.4 FR-1 「조립 지점을 한 곳으로」의 실질 — 아키텍처 테스트

#10 이 어댑터에서 스크럽하는 것은 **송신 일원화**이지 조립 일원화가 아니다.
조립을 우회하는 진짜 구멍은 **`com.anthropic` SDK 를 LLM 어댑터 밖에서 직접 쓰는 것**이다.

현재 사용처는 둘뿐이다 — `agent/adapter/out/llm/AnthropicLanguageModel.java` 와
`config/LanguageModelConfig.java`(조립 전용, architecture.md 가 허용).
**이 경계를 테스트로 고정한다.** 세 번째 사용처가 생기면 빌드가 깨진다.

### 3.5 FR-5 로그 — 지금 유출은 없고, 그것을 고정한다

확인 결과 **현재 프롬프트 전문·외부 본문을 찍는 `log.*` 는 없다.**
`TokenRedactingPromptScrubber` 는 길이만, `GitHubRepositorySource` 는 크기만 찍는다.
포맷 문자열에 외부 텍스트를 넣는 곳도 없다(로그 인젝션 없음).

문서 한 줄만 고치고 끝내면 「앞으로 빠질 수 없게」라는 이 PR 의 자기 규정과 어긋나므로,
**프롬프트 경로 두 패키지**(`agent/adapter/out/llm` · `agent/application`)에 한해
`log.*` 인자에 프롬프트·본문성 식별자가 오는지 소스 수준으로 검사한다.

⚠️ 소스 텍스트 검사라 **취약하다.** 다만 취약함의 방향이 「조용히 통과」가 아니라
「무고하게 빨개짐」이고, 대상 패키지를 둘로 좁혀 폭발 반경을 줄였다. 한계를 javadoc 에 적는다.
